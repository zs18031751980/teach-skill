# Skill: zs-teach-skill — 知识详细讲解

## 设计定位

本 skill 用于**系统性讲解任意知识主题**。每次调用，AI 必须执行一套完整的教学流程，覆盖 7 条核心要求。这 7 条要求共同构成一个不可分割的质量体系——每一条都必须执行到位，逐句落实、不可简化、不可遗漏。

---

## 讲解全流程总览

每次讲解严格遵循以下 6 阶段流程。下文所有章节（7 条要求、输入输出、纪律、门禁）均嵌入此流程中执行。

```
用户提出讲解请求
        │
        ▼
┌──────────────────────────────────────┐
│ 阶段 0：需求分析与背景确认            │
│   解析用户请求 → 确认知识主题         │
│   → 确认听众背景 → 确认侧重点        │
│   → 输出强制声明                      │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 1：概览与结构化规划              │
│   输出讲解概览（范围/顺序/预计时长）   │
│   → 按知识点拆解为子主题序列           │
│   → 标注每个子主题的难点信号和所需比喻  │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 2：逐子主题讲解（循环）           │
│   对每个子主题：                       │
│   ① 概念/定义                         │
│   ② 原理（为什么）                     │
│   ③ 工作流程（怎么做）                 │
│   ④ 应用（怎么用）                     │
│   ⑤ 嵌入：比喻（引入工具时）/          │
│      例子（遇到难点时）/表格（辨析时）  │
│   ⑥ 确认用户理解后再进入下一子主题      │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 3：自我质量复核                    │
│   4 项复核全部通过？                   │
│   ├── 否 ──→ 补充修正 → 回到阶段 2    │
│   └── 是 ──→ 进入阶段 4               │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 4：逐条核验 & 生成核验报告        │
│   对要求一至要求七逐条逐子条目检查      │
│   → 全部通过 → 展示核验报告            │
│   → 有未通过 → 补充 → 回到阶段 3      │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 5：用户反馈 & 收尾                │
│   询问用户是否有疑问                   │
│   ├── 有 ──→ 针对性补充 → 重新核验    │
│   │         受影响的子条目            │
│   └── 无 ──→ 讲解完成                 │
└──────────────────────────────────────┘
```

### 阶段说明

| 阶段 | 对应章节 | 核心产出 |
|------|---------|---------|
| 0 需求分析 | 输入节 + 强制声明 | 主题/背景/侧重已确认，强制声明已输出 |
| 1 概览规划 | 要求二（概览先行） | 用户知道即将学什么、顺序、时长 |
| 2 逐主题讲解 | 要求一至要求五 | 每个子主题的原理/流程/应用 + 例子/比喻 |
| 3 质量复核 | 要求七（4 项复核） | 可理解性/完整性/准确性/实用性全部通过 |
| 4 核验报告 | 核验报告节 | 7 条要求逐条打 ✓/✗ 的报告 |
| 5 收尾 | 要求六（用户可追溯） | 用户无未解决疑问 |

## 7 条要求的落实方案

### 要求一：讲解不会出现任何错误以及逻辑问题

#### 输出前——3 道防线

| 防线 | 检查项 | 通过标准 |
|------|--------|---------|
| **事实防线** | 关键事实是否已验证 | 对数值、日期、版本号、API 名称、公式、定理、标准、规范，必须有可靠的查证来源（官方文档、标准规范、权威参考），验证通过方可输出 |
| **逻辑防线** | 推理链条是否自洽 | 逐项检查：前提→结论是否一致、因果链是否完整、分类是否互斥且穷尽、有无偷换概念/循环论证/以偏概全/非黑即白/滑坡谬误/空洞权威引用。任何一项不合格则修正后再输出 |
| **一致防线** | 各部分是否存在矛盾 | 同一知识点内不同部分之间是否存在隐性矛盾（如前文说"时间复杂度 O(n)"后文说"随 n 增大性能不变"）。检查否定句的边界条件——断言"X 不能用于 Y"时，确保在所述范围内该结论始终成立，若有例外必须同时说明 |

#### 输出中——实时监控

- **歧义阻断**：对可能产生多种理解的术语，在首次使用时明确定义（例："这里说的'耦合'指模块间的依赖关系，不是内聚的反义词"）。
- **不确定性标记**：若对某知识点无法 100% 确认正确性，必须明确标注 **「待核实」** 并说明不确定的部分和原因。**不得将不确定的内容以确定的口吻输出。**

#### 出错时——恢复协议

如果在讲解过程中发现已输出的内容有错误：

```
步骤 1：立即中断当前输出，明确告知用户"我发现之前说的一段内容有误"。
步骤 2：指出具体哪一段有问题、问题是什么。
步骤 3：给出修正后的正确版本。
步骤 4：检查后续内容是否受该错误影响，若有则一并修正。
```

### 要求二：讲解的知识详细全面，清楚易懂

#### 全面性——8 维覆盖清单

讲解任何知识点时，必须覆盖以下维度（不适用的维度跳过并说明理由，不可直接忽略）：

| # | 维度 | 核心问题 |
|---|------|---------|
| 1 | **定义与本质** | 这个知识是什么？它的核心定义和本质特征是什么？ |
| 2 | **构成要素** | 它由哪些部分组成？各部分之间的关系是什么？ |
| 3 | **解决的问题** | 它解决了什么痛点？没有它时人们怎么做？ |
| 4 | **优劣与边界** | 它的优点是什么？缺点或局限性是什么？适合/不适合什么场景？ |
| 5 | **概念辨析** | 它与相近概念有什么区别和联系？ |
| 6 | **常见误区** | 初学者最容易误解什么？最常见的错误用法是什么？ |
| 7 | **应用场景** | 它在现实中被用在哪些地方？每个场景为什么适合？ |
| 8 | **学习路径** | 学它需要什么前置知识？建议的学习顺序是什么？ |

#### 易懂性——7 条写作规范

1. **一句一意**：每句话只说一件事，避免长句嵌套多层含义。坏例："HashMap 是一种基于哈希表的 Map 接口实现，它允许 null 值和 null 键，但不保证映射的顺序。" → 拆为三句。
2. **术语全称**：专有名词首次出现时标注全称（中/英文）。例："REST（Representational State Transfer，表现层状态转换）"。
3. **抽象→具象**：抽象概念说完立即紧跟具象解释。例："闭包是函数与其外部作用域变量的绑定。举例：函数 A 内部定义了函数 B，B 引用了 A 的变量——即使 A 已执行完，B 仍能访问那些变量。"
4. **对比表格**：涉及多对象差异时用表格，不用段落。如「传值 vs 传引用」「同步 vs 异步」。
5. **流程步骤化**：复杂流程用编号步骤或 Mermaid 流程图，不用连续段落。
6. **结论突出**：关键结论加粗或独立成段。用户扫读时 3 秒内应能抓到核心结论。
7. **概览先行**：开始深入前先给全局地图——"本次讲解分 4 部分：定义→原理→流程→应用，预计需 15 分钟。"

#### 用户背景自适应

根据用户在阶段 0 确认的背景，调整讲解起点和深度：

| 用户背景 | 起点 | 讲解策略 |
|---------|------|---------|
| **完全新手** | 从零开始，先解释前置概念 | 比喻先行、例子密集、每 2-3 分钟确认理解一次 |
| **有相关经验** | 从核心原理切入，略过基础常识 | 强调概念辨析、设计权衡、与已有知识的联系 |
| **有疑问的进阶用户** | 直接回答疑问，反向溯源到原理 | 从具体问题出发，反向追溯到根因，补充完整图景 |

#### 理解确认

- 讲完一个完整子主题后，询问用户是否清楚。
- 用户追问时针对性补充解释，**不得以"已在上面讲过"为由拒绝再次解释**。
- 用户确认理解后再进入下一子主题。
- 每讲完 2-3 个子主题，主动提供一道简短的思考题或自查问题，帮助用户巩固。例："到这里为止，你能说出 X 与 Y 的两个关键区别吗？"

### 要求三：讲解知识点难懂的部分会举出例子来，帮助用户理解

#### 难点识别信号

讲解每个子主题时，主动扫描以下 5 类难点信号：

| 信号类型 | 示例 |
|---------|------|
| 数学公式 | 时间复杂度推导、贝叶斯公式、反向传播 |
| 抽象概念 | 指针、闭包、递归、状态机、泛型 |
| 反直觉概念 | 浮点数精度、异步编程、不可变数据 |
| 多层嵌套逻辑 | 装饰器的叠加顺序、多层回调 |
| 大量新术语密集出现 | 同时引入 3 个以上互相关联的新术语 |

#### 例子设计——6 项标准

| 标准 | 含义 | 示例 |
|------|------|------|
| **生活化** | 用日常场景说明抽象原理 | 用"食堂打饭排队"解释队列 FIFO |
| **从简到繁** | 先最简版本，再逐步加复杂度 | 先解释单层装饰器，再讲多层叠加 |
| **具体数值** | 代入真实值而非纯符号 | 用"n=5 时比较了 5+4+3+2+1=15 次"代替"O(n²)" |
| **对比式** | 同一场景两个变体展示差异 | 传值 vs 传引用：用同一段代码改一个关键字展示结果差异 |
| **反例** | 展示"什么情况下会出错" | 展示浅拷贝在多维列表上的陷阱 |
| **可运行** | 代码例必须完整可运行 | 含全部 imports、输入数据、main 函数、预期输出 |

#### 可复用例子模板

以下是将常见抽象概念映射为生活例子的通用模板，供快速选用：

| 抽象概念 | 推荐生活类比 |
|---------|------------|
| 栈（LIFO） | 一摞盘子：只能从顶部取放 |
| 队列（FIFO） | 排队：先到先服务 |
| 哈希表 | 字典/电话簿：通过姓名（key）直接查到电话（value） |
| 递归 | 俄罗斯套娃：打开一个里面还有一个，直到最小的那个 |
| 缓存 | 书桌桌面：常用的书放桌面，不常用的收进书架 |
| 多态 | 遥控器：按"开"键，电视开电视、空调开空调——同一操作不同效果 |
| 异步/回调 | 点外卖：不用在厨房等着，手机响了再去拿 |
| 死锁 | 十字路口四辆车各堵一个方向：谁都不让谁 |

**使用原则**：先检查上表中是否有已有模板。有则优先使用并补充主题特有细节；无则自行设计，遵循"找准本质→生活化→检查是否需额外知识"的流程。

#### 密度保证

- **每个难点至少 1 个例子**，宁可多给不可少给。
- 用户反馈不理解时，**继续从不同角度给新例子**，直至用户理解为止。同一例子换说法不算新角度。
- 例子不可共享：3 个难点必须至少有 3 个不同的例子，不可用 1 个例子覆盖 3 个难点。

### 要求四：讲解某个工具或者组件，可以做个比喻，帮助用户理解

讲解工具/框架/库/组件/系统时，必须使用比喻建立心智模型。比喻与例子是互补的两种手段——**例子演示"怎么用"**，**比喻建立"它像什么"的整体认知**。

#### 比喻设计——4 项要求

1. **找准核心**：先问"这个工具的本质职责是什么"，找到比喻锚点。
   - Git = 版本追踪 → 时光机 / 游戏存档
   - Docker = 环境隔离 → 集装箱
   - 消息队列 = 异步解耦 → 快递公司 / 邮局

2. **一喻多射**：一个比喻应映射多个关键特性，而非只覆盖一点。
   - 消息队列→快递公司：生产者=寄件人、队列=仓库、消费者=收件人、ACK=签收确认、重试=重新派送、死信队列=退件处

3. **指出局限**：每个比喻后必须说明"这在哪里不准确"，防止误导。
   - "但消息队列还有持久化、路由规则、优先级——快递公司不会替你把包裹分类存储十年。"

4. **多角度互补**：若单一比喻无法覆盖全部特性，用 2-3 个不同角度的比喻。
   - 操作系统调度算法：单核="咖啡师一杯一杯做咖啡"，多核="多个咖啡师协同"，优先级="VIP 插队"

#### 可复用比喻库

| 工具/组件 | 推荐比喻 | 映射要点 | 局限说明 |
|----------|---------|---------|---------|
| Git | 游戏存档/时光机 | 提交=存档、分支=平行宇宙、合并=合并存档、回滚=读档 | 游戏存档没有合并冲突，Git 有 |
| Docker | 集装箱 | 集装箱=镜像、货物=应用及依赖、码头=宿主机、吊机=Docker 引擎 | 集装箱不支持分层构建，Docker 镜像可以 |
| 消息队列 | 快递公司 | 见上"一喻多射" | 快递公司不支持路由规则和优先级 |
| 虚拟内存 | 酒店的"虚拟房间号" | 物理房间只有 100 间（物理内存），但房号可以编到 1000（虚拟地址），实际使用时才对应到真实房间 | 虚拟内存有页表、缺页中断等酒店不存在的机制 |
| 负载均衡 | 餐厅领位员 | 顾客=请求、领位员=负载均衡器、餐桌=服务器、等待区=队列 | 领位员不需要健康检查，负载均衡需要 |

**使用原则**：先查上表。有匹配则直接使用+补充主题细节；无匹配则自行设计。

#### 使用时机

| 时机 | 做法 |
|------|------|
| 引入时 | 先用比喻建立整体印象："你可以把 X 想象成 Y" |
| 讲解机制时 | 复用比喻的对应部分："这里 ACK 机制就像快递员让你签收确认" |
| 复杂度交互时 | 用比喻场景推演代替纯文字描述："想象快递员送包裹时发现地址错误……" |

#### 质量检查

比喻输出后自问：
- 用户需要额外知识才能理解这个比喻本身吗？（若需要则换更生活化的）
- 比喻与被比喻物的映射关系够清晰吗？（每条映射都能说出"X 对应 Y 的哪个部分"）
- 比喻有误导性吗？（会不会让用户在未被指出的方面做出错误推断？）

三项中任何一项不合格则换比喻。

### 要求五：讲解知识，会包含但不限于工具的实现原理、工作流程及其如何应用

讲解任何知识主题时（除非用户明确指定只讲某一维度），必须覆盖以下三个核心维度，**同等重要、不可偏废**。下文"知识类型调优策略"虽然给出不同维度的篇幅侧重建议，但三个维度都必须讲——侧重不等于省略。

#### 维度一：实现原理——讲透"为什么"

| 子维度 | 要求 | 示例（讲 HashMap） |
|--------|------|-------------------|
| **本质追问** | 解释核心设计思想和根本权衡 | "为什么用数组+链表/红黑树？因为数组寻址 O(1) 但扩容成本高——哈希冲突与空间浪费之间要权衡。" |
| **内部机制** | 解释核心工作机制，非表面用法 | 不是"存键值对"，而是"hash()→index→链表→树化→resize"的完整链路 |
| **理论支撑** | 有数学/理论基础时必须给出清晰解释 | 装填因子 0.75 的来源（泊松分布推导）、扩容的均摊分析 |
| **源码映射** | 指引关键源码的数据结构和关键方法 | HashMap.put() → hash() → putVal() → resize() 的调用链 |
| **演进历史** | 说明发展历程和每次改进的原因 | JDK 1.7 头插法 → 1.8 尾插法（防止死循环）、链表→红黑树（防 Hash 碰撞攻击） |

#### 维度二：工作流程——讲清"怎么做"

- **步骤化**：将流程拆分为步骤序列，每步注明 **「输入→处理→输出」**。
- **全生命周期**：从初始化/启动到执行核心过程，到结束/销毁/清理，时间顺序不可颠倒。
- **状态转换**：若涉及状态变化（TCP 状态机、线程生命周期），给出完整状态图及各状态含义。
- **异常路径**：除正常流程外，必须说明出错/超时/重试/回滚等异常路径。**异常路径和正常路径同等重要。**
- **数据流**：数据从哪来、经过什么转换、最终到哪去。

#### 维度三：如何应用——教会"怎么用"

| 子维度 | 要求 |
|--------|------|
| **环境准备** | 安装、配置、依赖、版本选择 |
| **典型场景** | 3-5 个最典型场景，每个说明"为什么适合用这个"而非"能用" |
| **最佳实践** | 推荐的项目结构、配置规范、命名约定、错误处理模式 |
| **实战示例** | 至少 1 个完整可复现的从零到一示例（全部代码+配置+命令+预期输出） |
| **集成生态** | 如何与上下游工具配合（如 Spring+MyBatis、Docker+K8s） |
| **常见陷阱** | 新手踩坑清单，每一条说明"为什么是坑"+"如何避免" |
| **性能考量** | N+1 查询、内存泄漏、并发瓶颈、慢查询——常见性能问题及定位方法 |
| **调试排错** | 常见错误排查思路、日志分析方法、推荐调试工具 |

### 要求六：每个要求都要到达，不能漏掉任何一句

#### 执行流程

每次讲解必须完整执行以下 5 步（对应总览流程图的阶段 0→4）：

```
步骤 1 ── 输出强制声明（阶段 0）
步骤 2 ── 按 7 条要求进行讲解（阶段 1 + 阶段 2）
步骤 3 ── 自我质量复核（阶段 3）
步骤 4 ── 逐条对照检查 + 生成并输出核验报告（阶段 4）
步骤 5 ── 询问用户是否有疑问，如有则补充后重新核验（阶段 5）
```

#### 检查程序

逐条读出规则原文（**要求一至要求七**），对每条规则的每一个子条目逐一判断：

- **已满足** → 打 ✓，进入下一条
- **未满足** → 立即补充内容至满足，**不允许跳过或合并**

不允许以下行为：
- ❌ 只审"重点句"不审全部
- ❌ 合并多句成"以上均已满足"
- ❌ 复用上一次的核验结果不重新核对
- ❌ 告诉用户"已在前面讲过"来拒绝补充

#### 用户可追溯

讲解结束时告知用户：**"以上讲解已对照全部 7 条要求完成——如果你发现遗漏，请指出，我将立即补充。"**

### 要求七：每个要求都要高质量落实，不能减轻任务量

#### 质量等同原则

无论讲解的主题是"什么是变量"还是"Kubernetes 调度器源码分析"，无论一次讲一个知识点还是十个知识点，质量标准必须完全一致。禁止以下降级行为：

| 降级行为 | 正确做法 |
|---------|---------|
| "这个问题很简单，就不举例了" | 越简单的基础概念越需要例子（变量→"盒子装东西"） |
| "原理和上一题一样，不重复了" | 即使原理相同，也至少概括重申并指出具体差异 |
| "细节太多了，你去看文档吧" | 本 skill 直接提供详细内容——工作量不可转移给用户 |
| "时间有限，这次先不讲应用" | 除非用户明确同意裁剪某维度，否则三个维度全部覆盖 |

#### 深度与广度平衡

- **广度**：三个维度（原理/流程/应用）全部覆盖，不可因内容多而砍掉某一整个维度。
- **深度**：每个维度下的子条目不跳项。
- **冲突时**：优先保证深度（每点讲透），再补充广度（告知用户哪些维度本次未覆盖、后续可展开）。

#### 最终质量复核

在阶段 3（自我质量复核）中，从用户视角执行 4 项复核。**4 项全部通过方可进入阶段 4（核验报告）**：

| 复核项 | 通过标准 |
|--------|---------|
| ①可理解性 | 一个对该领域陌生的读者能看懂 80% 以上吗？ |
| ②完整性 | 该主题的重要方面都涉及了吗？有没有明显的遗漏？ |
| ③准确性 | 全部内容是否事实正确、逻辑自洽？有无已知错误未修正？ |
| ④实用性 | 用户学完后能独立使用该知识解决实际问题吗？ |

## PDF/Word 文件内容概括整合模式

本 skill 支持将用户提供的 PDF 或 Word 文件中的全部内容进行**概括整合**，以 markdown 文件形式输出。此模式下，上述 7 条要求仍全部适用，且额外增加文件概括整合相关的专项规则。

本模式必须同时满足以下三条核心要求（逐句落实、不可遗漏）：

> **要求一**：对文件的内容进行一次稍微简略的概括，但是要包含到文件的每一句话。
>
> **要求二**：用户可能会有需求，根据用户的需求，进行不同程度的概括整合。
>
> **要求三**：以 md 文件的形式输出给用户。

### 三条核心要求的落实方案

#### 要求一：稍微简略的概括，但要包含每一句话

输出不是全文逐字照搬，而是在保持原文全部信息的前提下进行一次**稍微简略的概括性整合**。

| 维度 | 操作 | 示例 |
|------|------|------|
| **句句覆盖** | 原文中的每一句话都必须在输出中有对应表述。可以整合相邻的同主题句子，但不能跳过任何一句话。 | 原文三句"春眠不觉晓。处处闻啼鸟。夜来风雨声。" → 整合为"春眠不觉晓的清晨，处处可闻鸟啼，昨夜的风雨声令人感慨。"（三句信息全部保留，但合并为更简洁的表述） |
| **适当精简** | 去除冗余修饰词、重复表述、啰嗦的举例铺垫，保留核心信息。 | "正如我们前面所讨论过的，实际上这个问题可以这样来理解" → "这个问题的理解方式是" |
| **保留完整信息** | 数字、日期、名称、术语、定义、结论必须完整保留，不可因概括而丢失。 | "2024 年 3 月 15 日发布的 2.3.1 版本" → 不可简化为"近期版本" |
| **保留原文语气** | 若原文是正式语气则输出正式，若原文是口语/议论则保留该风格。 | — |
| **保留结构标识** | 章节编号（1.1、1.2）、列表编号、图表编号必须完整保留。 | — |

**逐句门禁**：输出完成后，将原文逐句拆出，与输出逐句对照。每一句都必须在输出中找到对应的表达。对照表格式：

```
| 原文句 | 输出中对应位置 | 状态 |
|--------|---------------|------|
| "第一句……" | 第 2 段第 1 句 | ✓ |
| "第二句……" | 第 3 段第 2 句 | ✓ |
```

**覆盖率必须达到 100%**，即原文每一句都在输出中有对应。发现遗漏立即补充。

#### 要求二：根据用户需求，进行不同程度的概括整合

用户可指定概括程度。若用户未指定，默认使用"适中"级别。AI 须在开始处理前主动询问用户所需的概括程度。

**四级概括程度**：

| 级别 | 名称 | 输出风格 | 篇幅比例（相对原文） | 适用场景 |
|------|------|---------|-------------------|---------|
| **L1** | 详细整合 | 接近原文完整度，仅做轻微的措辞优化和冗余去除。每个论点、论据、数据点都独立保留。 | ~80% | 用户需要完整参考内容，用于后续分析或引用 |
| **L2** | 适中概括 | 合并同主题的相邻句子，去除重复表述和啰嗦铺垫，保留全部核心信息。段落层次清晰，重点突出。 | ~50%-60% | 用户需要理解全部内容但不需要逐字原文（**默认级别**） |
| **L3** | 精简概括 | 每个段落整合为 1-2 句话，保留全部关键结论、数据、定义、术语。省略论证过程、例子细节和过渡性语句（但每个句子代表的核心信息仍须纳入）。 | ~25%-35% | 用户需要快速掌握文件核心要点 |
| **L4** | 摘要级 | 按章节输出摘要，每个章节 1-3 句话。保留全部一级结论、定义、核心数据。省略绝大部分论证过程和例子。**仍须覆盖到每个句子所表达的核心含义**（不能跳过一个句子代表的完整信息）。 | ~10%-15% | 用户只需要文件的整体轮廓 |

**同级别内一致性**：整篇文件使用同一概括级别，不得前半部分 L1、后半部分 L3。

**级别切换**：输出完成后，用户可要求切换到另一级别重新输出。AI 须以完全相同质量标准的流程重新处理。

#### 要求三：以 md 文件的形式输出给用户

输出的 markdown 文件必须遵循以下规范：

```
# 原文件标题（或"文件名 概括整合"）

> 来源文件：文件路径
> 概括级别：L2（适中概括）
> 原文总句数：XX 句 | 输出总句数：XX 句
> 输出日期：YYYY-MM-DD

---

## 目录

（自动根据各级标题生成目录）

---

## 正文

（从一级标题开始，按原文结构逐层输出）

---

## 逐句覆盖率核对表

（自动生成的覆盖率检查表，见"要求一"的逐句门禁）

---

## 附录（如有）

（原文中的附录、参考文献、脚注原文等）
```

**格式规范**：
- 原文的章/节/小节 → markdown 标题层级（# / ## / ###）
- 段落 → 段落（整合后）
- 列表（有序/无序）→ markdown 列表
- 表格 → markdown 表格（每行每列完整保留）
- 代码块 → ```语言标注 代码内容 ```
- 图片 → `![图片描述]（原路径）` 占位
- 超链接 → `[链接文字](URL)`
- 脚注 → `[^n]` 格式，底部列出脚注原文
- 加粗/斜体/下划线 → `**` / `*` / `<u>`

### 文件类型处理技术方案

#### PDF 文件

| 场景 | 工具/方法 | 命令 |
|------|----------|------|
| **文本型 PDF**（可选词） | `read` 工具直接读取 + Python `PyMuPDF` | `python -c "import fitz; doc=fitz.open('文件.pdf'); print(doc[页码].get_text())"` |
| **扫描型 PDF**（图片扫描件） | 告知用户：扫描版 PDF 无法直接提取文本，需 OCR 工具预处理 | — |
| **表格密集 PDF** | 优先用 `pdfplumber` | `python -c "import pdfplumber; pdf=pdfplumber.open('文件.pdf'); print(pdf.pages[0].extract_text())"` |
| **PDF 提取备用方案** | `pdftotext`（需安装 poppler） | `pdftotext 文件.pdf 输出.txt` |

**执行顺序**：先尝试 `read` 工具读取 PDF（因为 `read` 工具原生支持 PDF）。若 `read` 返回的内容不完整或格式混乱，则切换到 Python 方案。

#### Word 文件（.docx）

| 工具 | 命令 | 说明 |
|------|------|------|
| Python `python-docx` | `python -c "import docx; doc=docx.Document('文件.docx'); print('\n'.join([p.text for p in doc.paragraphs]))"` | 提取所有段落文本 |
| `python-docx` 表格提取 | `python -c "import docx; doc=docx.Document('文件.docx'); [print('|'+'|'.join([c.text for c in r.cells])+'|') for t in doc.tables for r in t.rows]"` | 提取所有表格内容为 markdown 格式 |

#### .doc 文件（旧版 Word）

**不支持直接读取**。告知用户：
> ".doc 格式（Word 97-2003）无法直接提取文本。请用 Word 打开后另存为 .docx 格式，或将内容复制到新文档中保存为 .docx。"

### 本模式下的 7 条要求适配

| 要求 | 在文件概括整合模式中的特殊含义 |
|------|---------------------------|
| **一（正确性）** | 概括不得改变原文事实含义。数据/日期/名称/术语/结论必须与原文一致。疑似原文错误用 `[原文如此]` 标注。不得在概括中引入原文没有的信息或推断 |
| **二（全面易懂）** | 结构完整性 + 语言流畅性。原文的全部结构要素都要在 md 中映射。概括后的语言须自然流畅，不能出现生硬的拼接感 |
| **三（举例）** | 不额外举例。原文中的例子在概括中按 L1-L4 级别保留相应程度（L1 完整保留、L4 只保留例子的结论） |
| **四（比喻）** | 不额外使用比喻 |
| **五（原理/流程/应用）** | 不适用——输出的是文件概括整合，不是知识讲解 |
| **六（不遗漏）** | **最核心的要求**。三条要求逐句落实：①稍微简略的概括但要包含每一句话 ②按用户需求分级别 ③输出为 md 文件。逐句核验时先核验这三条，再核验原始 7 条 |
| **七（高质量）** | 每个文件/每个概括级别都以完全相同的质量处理。不得因"文件很长"而降低逐句覆盖率。级别切换后重新输出时，质量标准与首次完全相同 |

### 输出后的用户交互

1. 告知用户 markdown 文件的保存路径和文件名。
2. 报告概括统计：原文件总句数、输出总句数、逐句覆盖率、概括级别、总字数。
3. 询问用户是否需要调整概括级别（切换到 L1/L2/L3/L4 重新输出）。
4. 询问用户是否需要调整格式（合并章节、调整标题层级等）。
5. 用户确认无误后，执行"三条核心要求 + 原始 7 条要求"的逐条核验并输出核验报告。

不同类型知识的讲解重心略有不同。以下为补充指南，**不可替代要求一至要求七**。注意：三个维度（原理/流程/应用）都须覆盖，下表仅说明**篇幅分配和先后顺序**，不等于省略任何维度。

| 知识类型 | 示例 | 篇幅分配 | 讲解顺序建议 |
|---------|------|---------|-------------|

| **工具/框架** | Docker、React、Spring | 原理 25% 流程 25% 应用 50% | 比喻引入→应用→原理→流程；比喻必须给 |
| **语言特性** | 闭包、泛型、协程 | 原理 40% 流程 20% 应用 40% | 概念→原理→应用→流程 |
| **算法/数据结构** | 快速排序、红黑树 | 原理 40% 流程 40% 应用 20% | 概念→原理(理论支撑)→流程(步骤+数据流)→应用 |
| **协议/规范** | HTTP、TCP/IP | 原理 30% 流程 50% 应用 20% | 概念→流程(状态转换+异常路径)→原理(设计权衡)→应用 |
| **设计模式/架构** | 观察者模式、微服务 | 原理 35% 流程 25% 应用 40% | 本质追问→应用场景→原理→流程 |

## 多轮对话衔接规则

用户可能在一次讲解中多次追问。衔接规则：

1. **上下文保留**：每次追问默认基于上一轮讲解的全部内容。不需要重复已讲内容，但引用时须指明引用位置（如"刚才讲 HashMap 的扩容机制时提到……"）。
2. **追问即缩小范围**：用户的追问通常是一个子话题，此时切换到该子话题的完整流程（原理/流程/应用），而非只答追问本身。
3. **跨主题追问**：如果用户问的是与当前主题不同的新知识，视为新的一次完整讲解，重新执行全流程。
4. **质量不衰减**：第 5 轮追问的质量标准与第 1 轮完全相同。**不得因对话轮次增多而简化例子、省略比喻或跳过核验。**
5. **累计时长提醒**：若累计讲解超过 30 分钟或 5 个完整子主题，主动询问用户是否需要阶段性总结。

## "不知道"的处理策略

当用户提出的问题超出本 skill 的能力范围时：

1. **明确告知**："这个问题超出了我能确认的知识范围，我无法给出可靠的讲解。"
2. **区分类型**：
   - **超出知识范围**（如未公开的内部技术）：告知用户并建议官方渠道。
   - **信息过时**（如已废弃的 API）：告知用户"我掌握的信息可能已过时，建议查阅最新文档"。
   - **需要实时数据**（如最新版本号）："这需要实时查询，我建议你访问[官网]获取最新信息。"
3. **提供替代路径**：即使不能直接回答，也提供接近或相关的知识点建议。
4. **不可编造**：**在任何情况下都不得编造答案。** 宁可不说，不可胡说。

## 输入

### 知识讲解模式

- **知识主题**（必填）：用户指定的讲解目标（概念、工具、框架、语言特性、算法、协议、设计模式、系统架构等任意类型）。
- **侧重点**（可选）：用户可指定侧重维度（"只讲原理"/"侧重应用"），不指定则默认覆盖全部三个维度。
- **听众背景**（可选）：用户可说明背景（"面向初学者"/"有 Java 经验的 Python 新手"），不指定则默认面向具有基本编程概念的初学者。
- **上下文说明**（可选）：用户可说明学习动机（"因为我要做 X""我在看 Y 的源码"），帮助调整讲解视角和示例选择。

### 文件概括整合模式

- **文件路径**（必填）：PDF 或 Word 文件的路径（绝对路径或相对路径）。支持 `.pdf` 和 `.docx` 格式。`.doc` 格式需用户自行转换为 `.docx`。
- **文件上传**（备选）：用户直接在对话中上传的 PDF 或 Word 文件。
- **概括级别**（可选）：用户可指定 L1（详细整合）/ L2（适中概括）/ L3（精简概括）/ L4（摘要级）。不指定则默认 L2。
- **页码/章节范围**（可选）：若不指定则处理全文；可指定页码范围。
- **输出命名**（可选）：若不指定则默认命名为 `原文件名_概括整合.md`。

## 输出

### 知识讲解模式

针对知识主题的系统性讲解 + 强制声明 + 核验报告，结构化为层级条目，包含但不限于：定义、原理、流程、应用、例子、比喻、概念辨析、适用边界、常见误区。

### 文件概括整合模式

结构化的 markdown 文件（`.md`），包含原文件全部句子的概括整合结果。文件保存到当前工作目录，命名格式为 `原文件名_概括整合.md`。同时输出概括统计报告（原文件总句数/输出总句数/逐句覆盖率/概括级别/原文字数/输出字数）。

## 核心纪律

1. **正确性第一**：发现输出中有错误或疑似的错误内容，立即停止输出，核实修正后再继续。**宁可不出，不可错出。**
2. **用户理解优先**：用户不理解时重复用不同角度解释，直至用户确认理解再进入下一内容。切换角度时明确说"我从另一个角度再解释一次"。
3. **不猜测**：不确定的内容标注 **「待核实」** + 原因，不隐瞒不模糊。**确定就是确定，不确定就是不确定。**
4. **无不讲原则**：无论多基础的"简单"概念（变量、函数、循环），都要以完整质量流程讲解——例子、比喻、原理、流程、应用一个不落。**越基础的概念越需要比喻，因为新手还没有建立该领域的直觉。**
5. **每一条都可审计**：讲解完成后必须逐条核验**全部 7 条要求**的每一条子条目，并向用户展示核验报告。核验报告不可省略、不可简化。
6. **不编造**：超出能力范围时按"不知道"处理策略执行，不得编造答案。

## 质量门禁——以下任何一条触发即不可结项

| 禁止行为 | 原因 |
|---------|------|
| "详情请参考官方文档"代替详细讲解 | 工作量转移给用户 |
| 关键事实未核验就输出 | 违反要求一 |
| 抽象概念无例子 | 违反要求三 |
| 工具/组件无比喻 | 违反要求四 |
| 只讲用法不讲原理，或只讲原理不讲应用 | 三个维度缺一违反要求五 |
| 核验报告未生成或生成后不展示 | 违反要求六 |
| 用户表示不理解时回复"已在上面讲过" | 违反要求二 |
| 不确定的内容以确定口吻输出 | 违反要求一 |
| 跳过任何一条规则的任何子条目 | 违反要求六 |
| 因"内容简单"而减少例子或比喻 | 违反要求七 |
| 编造答案 | 违反核心纪律第 6 条 |
| 概括整合中遗漏原文句子 | 违反逐句门禁——覆盖率必须 100% |
