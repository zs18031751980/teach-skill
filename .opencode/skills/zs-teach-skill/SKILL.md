# Skill: zs-teach-skill — 知识详细讲解 + 文件概括整合 + 代码解释 + 算法题讲解

## 自然表达（所有模式共用）

在不减少讲解内容、逐句覆盖或代码逐行解释的前提下，让文字顺着读者的理解过程展开。本节吸收 X-math-paper-deai 的具体表达、信息节奏、分级修改与保真检查，已改为教学场景可独立执行的规则，无需调用论文技能。

- **对象和动作说清楚**：用当前知识中的具体对象、操作与结果解释机制，避免只说“有效处理”“实现优化”。多个对象同时出现时，明确“它”“该方法”指谁；把条件放在它实际限定的动作附近。“对结果进行存储”可写为“保存结果”，但不拆改正式概念。
- **按真实关系衔接**：先回应问题，再按定义、依赖、原因或操作顺序展开。保留方法选择的理由和关键中间步骤；不靠每段重复“首先、其次、综上所述”推进，也不为换句式打乱推导。连接词有实际作用时正常保留。
- **详略服务于理解**：难点、反直觉处和关键选择充分解释，已交代的常规操作紧凑衔接。删去无信息的重复总结，保留承担不同作用的定义、推导、例子和必要复述。不能以“自然”为由跳过知识点、代码行或原文信息。
- **保持术语和语气稳定**：同一对象沿用同一名称，不轮换“模型、算法、系统”制造变化。语言可以亲切平实，不强制口语、反问、金句、第一人称或假想对话，不编造个人经历和学习感受。
- **句式与版式按需选择**：一句有清楚主干即可，不按字数拆句；段落承接连贯解释，列表呈现步骤或并列项，表格用于确需比较的内容。保留模式要求的逐行代码表和原文结构。标题写知识内容，不机械照抄内部检查项；长篇按需概览，短问题直接回答。
- **例子与比喻回到机制**：说明例子中的对象对应什么、哪一步体现原理；比喻之后讲清真实机制及对应边界。教学假设和演示数据应明确身份，不冒充真实测量、运行结果或来源事实，不用故事替代必要推导。

### 材料依据与读者衔接

先区分初稿已有信息、当前材料已有但初稿遗漏的信息、尚不能确定的信息。必要理由已有依据时，可在本次范围内补回；未知的作者意图、历史或运行结果不能靠顺口的叙述补造。缺少可选解释不阻塞其他内容，缺少关键依据时只指出受影响的判断。

检查读者能否从可见的前文理解下一步：关键术语未定义、条件未交代或推导跳步时，补足必要解释；前文已讲清的依据不逐段重述。不虚构“前文已经证明”。标准定义、定律和规范标题可以通用；只对本应说明当前对象却换个题名仍成立的空泛分析进行具体化。用户指定的标题、准确自然的并列句、被动句和必要加粗均保留。

比较时核对“数值—对象—指标—基线—条件”的配对：“降低20%”不等于“降低到20%”，“2个百分点”不等于“2%”。“未证明收敛”不等于“不收敛”。合并句子后，来源引用仍须只支持原来有依据的内容；方法文档不能被写成当前程序实测结果的证据。保留公式编号、代码标识符及其解释对应关系。

### 四种模式的具体落实

| 模式 | 表达重点 | 同次复核的重点 |
|------|----------|----------------|
| 知识讲解 | 从用户当前疑问展开，解释关键原因和必要前置知识；已有清楚定义不重复铺垫 | 读者能顺着可见关系理解结论，例子回到真实机制，常规内容不反复总结 |
| 文件概括 | 按原文语气和论证依赖衔接相邻句，消除拼接感；不从外部补原文没有的解释 | 改写后重新核对句子映射、否定与限定、数字配对及引用；不为篇幅比例牺牲信息 |
| 代码解释 | 语法列解释写法，逻辑列解释该行的实际作用、状态变化和上下文关系；不把同一句换词填两列 | 保留每个非空代码行及注释的对应解释；不以“同上”替代，不猜作者意图，不改源码 |
| 算法题 | 用题目条件解释方法选择，再联系变量、判断和状态转移；按真实推导组织标题与段落 | 建模与代码两条线完整、条件和复杂度限定准确；不编造试错史，不重复通报自检流程 |

这张表用于已有模式的表达与复核，不增加一轮后处理，也不把文件概括或代码解释扩展成额外教学任务。

### 同次复核中的一次表达检查

完成内容后，在已有质量复核中检查一次，不另启多轮“去味”：自然准确则保留；有语病、歧义或冗余时局部修改；段落确实空泛或顺序混乱时，在当前范围内依据已有材料重写。必要解释可以增加篇幅，不追求更短，不设禁词表、句长配额、修改比例或检测分数。

改前后对照定义、公式、数值、单位、否定、条件、比较方向、引用归属及代码实际行为。特别保留“仅、至少、近似、可能、在……范围内”等影响含义的限定，不把相关性改为因果或把有限结论写成普遍规律。语言润色不改代码、公式或原始数据；发现内容错误时另按正确性要求核实修正，不偷偷当作措辞修改。

新增一句若删去后仍不损失信息、指代和必要依赖，就去掉重复补充；替换若没有解决实际问题，就保留原表达。无法保真的改动撤销，继续处理其余部分。最终直接交付讲解，不展示润色过程、自评分或固定质量声明；用户要求审阅时再说明具体修改。

### 检查完成后只交付学习内容

所有模式先在内部完成适用检查，发现问题先修正并复核，再输出本轮讲解或文件。不要把检查项、逐项通过状态、打勾表、覆盖率统计或“全部检查通过”的结语放进对话、学习正文、文件附录或默认交付附件；也不要用列表或段落变相复述检查结果。内部覆盖映射可用于核对，默认不另存审计报告；用户明确要求查看检查依据时才单独提供。

这不影响知识对比表、逐行代码解释表、样例推演、正确性证明等实际教学内容。若存在无法核实的关键问题，如实简述影响和必要的缺失信息，不把有问题的内容当作已检查完成的成品交付，也不伪称全部通过。

### 教学表达示例

以下仅演示改写判断，不提供当前任务的事实：

- 空泛：“通过对队列机制的有效利用，实现任务的有序处理。” → 具体：“任务先进入队列，消费者再按出队顺序取出任务。”若讨论并发消费者，须区分取出顺序与完成顺序，不能据此保证任务按序完成。
- 指代不明：“函数创建了列表和迭代器，它保存当前位置。” → 明确：“迭代器记录当前遍历到的位置。”前提是所讲迭代器确实具有这一行为。
- 限定保留：“在数组有序的前提下，可以用二分查找缩小搜索范围。”不能为了简短删掉“数组有序”的前提。

## 设计定位

本 skill 用于**系统性讲解任意知识主题**。每次调用，AI 必须执行一套完整的教学流程，覆盖 7 条核心要求。这 7 条要求共同构成一个不可分割的质量体系——每一条都必须执行到位，逐句落实、不可简化、不可遗漏。

**输出纯净性原则（硬性约束）**：

1. **强相关**：最终面向用户的输出，必须**全部与用户本次提问直接相关**，只呈现知识正文（定义、原理、流程、应用、例子、比喻、辨析、边界、误区等），不得夹带任何与提问无关的元过程内容。
2. **流程照常、检查不省**：各项自检、4 项复核、逐条核验等质量保障步骤**照常执行**（不可偷减），其结果只用于内部修正与查漏补缺。
3. **禁止输出检查表格**：尤其禁止在讲解末尾向用户输出「要求核验报告」「逐条打 ✓/✗ 表」「覆盖率核对表」等检查项表格——这类表格与用户提问无关，会污染知识内容，必须省略。

**本 skill 共支持四种模式**（用户请求命中的模式自动生效，7 条要求在所有模式下均适用）：

| 模式 | 触发场景 | 核心产出 |
|------|---------|---------|
| **知识讲解模式** | 解释概念/工具/语言特性/协议等 | 系统性讲解（原理+流程+应用） |
| **文件概括整合模式** | 概括 PDF/Word/PPT 文件 | 逐句覆盖 100% 的 markdown 整合 |
| **代码解释模式** | 解释一段代码/一个文件 | 逐句语法+逻辑双维解释 |
| **算法题讲解模式** | 做算法题/写题解 | 建模思路 + 代码思路 + 完整代码 |

## 讲解全流程总览

每次讲解严格遵循以下 6 阶段流程。下文所有章节（7 条要求、输入输出、纪律、门禁）均嵌入此流程中执行。

```
用户提出讲解请求
        │
        ▼
┌──────────────────────────────────────┐
│ 阶段 0：需求分析（必要时澄清）          │
│   解析用户请求 → 确定知识主题         │
│   → 读取已提供背景/侧重点；缺关键才问 │
│   → 按主题自然开场                      │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 1：概览与结构化规划              │
│   输出讲解概览（范围/顺序，按需提供）   │
│   → 按知识点拆解为子主题序列           │
│   → 标注每个子主题的难点信号和所需比喻  │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 2：逐子主题讲解（循环）           │
│   对每个子主题：                       │
│   ① 概念/定义                         │
│   ② 原理（为什么）                     │
│   ③ 工作流程（怎么做）                 │
│   ④ 应用（怎么用）                     │
│   ⑤ 嵌入：比喻（引入工具时）/          │
│      例子（遇到难点时）/表格（辨析时）  │
│   ⑥ 分步教学按反馈推进；完整请求连续完成      │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 3：自我质量复核                    │
│   4 项复核全部通过？                   │
│   ├── 否 ──→ 补充修正 → 回到阶段 2    │
│   └── 是 ──→ 进入阶段 4               │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 4：逐条核验（内部，不输出）        │
│   对要求一至要求七逐条逐子条目检查      │
│   → 全部通过 → 进入阶段 5             │
│   → 有未通过 → 补充 → 回到阶段 3    │
└──────────┬───────────────────────────┘
           ▼
┌──────────────────────────────────────┐
│ 阶段 5：用户反馈 & 收尾                │
│   完整请求 → 交付；分步请求 → 等待反馈 │
│   ├── 有追问 ──→ 针对性补充 → 重新核验 │
│   └── 无追问 ──→ 讲解完成              │
└──────────────────────────────────────┘
```

### 阶段说明

| 阶段 | 对应章节 | 核心产出 |
|------|---------|---------|
| 0 需求分析 | 输入节 + 讲解开场 | 主题/背景/侧重已读取或采用默认，已按主题自然开场 |
| 1 概览规划 | 要求二（概览先行） | 长篇讲解有清楚的范围与顺序 |
| 2 逐主题讲解 | 要求一至要求五 | 每个子主题的原理/流程/应用 + 例子/比喻 |
| 3 质量复核 | 要求七（4 项复核） | 可理解性/完整性/准确性/实用性全部通过 |
| 4 内部核验 | 要求六（内部逐条核验） | 7 条要求逐条内部检查，不向用户输出报告 |
| 5 收尾 | 要求六（用户可追溯） | 请求范围已交付，后续疑问可修订 |

## 7 条要求的落实方案

### 要求一：讲解不会出现任何错误以及逻辑问题

#### 输出前——3 道防线

| 防线 | 检查项 | 通过标准 |
|------|--------|---------|
| **事实防线** | 关键事实是否已验证 | 对数值、日期、版本号、API 名称、公式、定理、标准、规范，必须有可靠的查证来源（官方文档、标准规范、权威参考），验证通过方可输出 |
| **逻辑防线** | 推理链条是否自洽 | 逐项检查：前提→结论是否一致、因果链是否完整、分类是否互斥且穷尽、有无偷换概念/循环论证/以偏概全/非黑即白/滑坡谬误/空洞权威引用。任何一项不合格则修正后再输出 |
| **一致防线** | 各部分是否存在矛盾 | 同一知识点内不同部分之间是否存在隐性矛盾（如前文说"时间复杂度 O(n)"后文说"随 n 增大性能不变"）。检查否定句的边界条件——断言"X 不能用于 Y"时，确保在所述范围内该结论始终成立，若有例外必须同时说明 |

#### 输出中——实时监控

- **歧义阻断**：对可能产生多种理解的术语，在首次使用时明确定义（例："这里说的'耦合'指模块间的依赖关系，不是内聚的反义词"）。
- **不确定性标记**：若对某知识点无法 100% 确认正确性，必须明确标注 **「待核实」** 并说明不确定的部分和原因。**不得将不确定的内容以确定的口吻输出。**

#### 出错时——恢复协议

如果在讲解过程中发现已输出的内容有错误：

```
步骤 1：立即中断当前输出，明确告知用户"我发现之前说的一段内容有误"。
步骤 2：指出具体哪一段有问题、问题是什么。
步骤 3：给出修正后的正确版本。
步骤 4：检查后续内容是否受该错误影响，若有则一并修正。
```

### 要求二：讲解的知识详细全面，清楚易懂

#### 全面性——8 维覆盖清单

讲解任何知识点时，必须覆盖以下维度（不适用的维度内部判断后跳过，仅当影响用户理解时说明理由，不可直接忽略）：

| # | 维度 | 核心问题 |
|---|------|---------|
| 1 | **定义与本质** | 这个知识是什么？它的核心定义和本质特征是什么？ |
| 2 | **构成要素** | 它由哪些部分组成？各部分之间的关系是什么？ |
| 3 | **解决的问题** | 它解决了什么痛点？没有它时人们怎么做？ |
| 4 | **优劣与边界** | 它的优点是什么？缺点或局限性是什么？适合/不适合什么场景？ |
| 5 | **概念辨析** | 它与相近概念有什么区别和联系？ |
| 6 | **常见误区** | 初学者最容易误解什么？最常见的错误用法是什么？ |
| 7 | **应用场景** | 它在现实中被用在哪些地方？每个场景为什么适合？ |
| 8 | **学习路径** | 学它需要什么前置知识？建议的学习顺序是什么？ |

#### 易懂性——7 条写作规范

1. **主干清楚**：对象、动作及条件容易辨认；嵌套确实妨碍理解时再拆句。连贯的定义、条件和因果可留在同一句中，不机械执行一句一意。
2. **术语全称**：专有名词首次出现时标注全称（中/英文）。例："REST（Representational State Transfer，表现层状态转换）"。
3. **抽象→具象**：抽象概念说完立即紧跟具象解释。例："闭包是函数与其外部作用域变量的绑定。举例：函数 A 内部定义了函数 B，B 引用了 A 的变量——即使 A 已执行完，B 仍能访问那些变量。"
4. **对比清楚**：多对象、多维差异适合表格；少量差异用连贯段落即可。
5. **流程清楚**：复杂流程用编号步骤或 Mermaid 流程图，步骤之间用必要文字说明依赖和原因。
6. **结论突出**：关键结论加粗或独立成段。用户扫读时 3 秒内应能抓到核心结论。
7. **按需概览**：长篇先简述学习范围和顺序，短问题直接回应；不为每个子主题重复固定目录。

#### 用户背景自适应

根据用户在阶段 0 确认的背景，调整讲解起点和深度：

| 用户背景 | 起点 | 讲解策略 |
|---------|------|---------|
| **完全新手** | 从零开始，先解释前置概念 | 比喻先行、例子密集、分步教学时按反馈调整；完整讲解不定时中断 |
| **有相关经验** | 从核心原理切入，略过基础常识 | 强调概念辨析、设计权衡、与已有知识的联系 |
| **有疑问的进阶用户** | 直接回答疑问，反向溯源到原理 | 从具体问题出发，反向追溯到根因，补充完整图景 |

#### 理解确认

- 完整讲解在子主题间简短衔接；分步教学时才询问是否清楚并等待。
- 用户追问时针对性补充解释，**不得以"已在上面讲过"为由拒绝再次解释**。
- 仅在用户选择逐步教学时，等待理解反馈后进入下一子主题；完整讲解、代码解释或文件整理默认连续完成，交付前自检。
- 在关键难点后，可按学习需要提供简短的思考题或自查问题，不按固定子主题数量插入。例："到这里为止，你能说出 X 与 Y 的两个关键区别吗？"

### 要求三：讲解知识点难懂的部分会举出例子来，帮助用户理解

#### 难点识别信号

讲解每个子主题时，主动扫描以下 5 类难点信号：

| 信号类型 | 示例 |
|---------|------|
| 数学公式 | 时间复杂度推导、贝叶斯公式、反向传播 |
| 抽象概念 | 指针、闭包、递归、状态机、泛型 |
| 反直觉概念 | 浮点数精度、异步编程、不可变数据 |
| 多层嵌套逻辑 | 装饰器的叠加顺序、多层回调 |
| 大量新术语密集出现 | 同时引入 3 个以上互相关联的新术语 |

#### 例子设计——6 项标准

| 标准 | 含义 | 示例 |
|------|------|------|
| **生活化** | 用日常场景说明抽象原理 | 用"食堂打饭排队"解释队列 FIFO |
| **从简到繁** | 先最简版本，再逐步加复杂度 | 先解释单层装饰器，再讲多层叠加 |
| **具体数值** | 代入真实值而非纯符号 | 用"n=5 时比较了 5+4+3+2+1=15 次"代替"O(n²)" |
| **对比式** | 同一场景两个变体展示差异 | 传值 vs 传引用：用同一段代码改一个关键字展示结果差异 |
| **反例** | 展示"什么情况下会出错" | 展示浅拷贝在多维列表上的陷阱 |
| **可运行** | 代码例必须完整可运行 | 含全部 imports、输入数据、main 函数、预期输出 |

#### 可复用例子模板

以下是将常见抽象概念映射为生活例子的通用模板，供快速选用：

| 抽象概念 | 推荐生活类比 |
|---------|------------|
| 栈（LIFO） | 一摞盘子：只能从顶部取放 |
| 队列（FIFO） | 排队：先到先服务 |
| 哈希表 | 字典/电话簿：通过姓名（key）直接查到电话（value） |
| 递归 | 俄罗斯套娃：打开一个里面还有一个，直到最小的那个 |
| 缓存 | 书桌桌面：常用的书放桌面，不常用的收进书架 |
| 多态 | 遥控器：按"开"键，电视开电视、空调开空调——同一操作不同效果 |
| 异步/回调 | 点外卖：不用在厨房等着，手机响了再去拿 |
| 死锁 | 十字路口四辆车各堵一个方向：谁都不让谁 |

**使用原则**：上表仅供选例。先判断例子是否准确对应当前难点、符合用户背景；匹配时复用并补足当前机制，不匹配时另选，不为套模板绕远路。

#### 密度保证

- **每个难点至少 1 次具体示例演示**，宁可多给不可少给。
- 用户反馈不理解时，**继续从不同角度给新例子**，直至用户理解为止。同一例子换说法不算新角度。
- 可用同一贯穿例子解释多个难点，但每个难点须有对应的具体步骤或变体，不能只展示一次就声称全部覆盖。

### 要求四：讲解某个工具或者组件，可以做个比喻，帮助用户理解

讲解工具/框架/库/组件/系统时，必须使用比喻建立心智模型。比喻与例子是互补的两种手段——**例子演示"怎么用"**，**比喻建立"它像什么"的整体认知**。

#### 比喻设计——4 项要求

1. **找准核心**：先问"这个工具的本质职责是什么"，找到比喻锚点。
   - Git = 版本追踪 → 时光机 / 游戏存档
   - Docker = 环境隔离 → 集装箱
   - 消息队列 = 异步解耦 → 快递公司 / 邮局

2. **一喻多射**：一个比喻应映射多个关键特性，而非只覆盖一点。
   - 消息队列→快递公司：生产者=寄件人、队列=仓库、消费者=收件人、ACK=签收确认、重试=重新派送、死信队列=退件处

3. **指出局限**：每个比喻后必须说明"这在哪里不准确"，防止误导。
   - "但消息队列还有持久化、路由规则、优先级——快递公司不会替你把包裹分类存储十年。"

4. **多角度互补**：若单一比喻无法覆盖全部特性，用 2-3 个不同角度的比喻。
   - 操作系统调度算法：单核="咖啡师一杯一杯做咖啡"，多核="多个咖啡师协同"，优先级="VIP 插队"

#### 可复用比喻库

| 工具/组件 | 推荐比喻 | 映射要点 | 局限说明 |
|----------|---------|---------|---------|
| Git | 游戏存档/时光机 | 提交=存档、分支=平行宇宙、合并=合并存档、回滚=读档 | 游戏存档没有合并冲突，Git 有 |
| Docker | 集装箱 | 集装箱=镜像、货物=应用及依赖、码头=宿主机、吊机=Docker 引擎 | 集装箱不支持分层构建，Docker 镜像可以 |
| 消息队列 | 快递公司 | 见上"一喻多射" | 快递公司不支持路由规则和优先级 |
| 虚拟内存 | 酒店的"虚拟房间号" | 物理房间只有 100 间（物理内存），但房号可以编到 1000（虚拟地址），实际使用时才对应到真实房间 | 虚拟内存有页表、缺页中断等酒店不存在的机制 |
| 负载均衡 | 餐厅领位员 | 顾客=请求、领位员=负载均衡器、餐桌=服务器、等待区=队列 | 领位员不需要健康检查，负载均衡需要 |

**使用原则**：上表是候选比喻，使用前核对映射和局限；贴合当前机制才采用，不直接照搬其中的局限描述。

#### 使用时机

| 时机 | 做法 |
|------|------|
| 引入时 | 先用比喻建立整体印象："你可以把 X 想象成 Y" |
| 讲解机制时 | 复用比喻的对应部分："这里 ACK 机制就像快递员让你签收确认" |
| 复杂度交互时 | 用比喻场景推演代替纯文字描述："想象快递员送包裹时发现地址错误……" |

#### 质量检查

比喻输出后自问：
- 用户需要额外知识才能理解这个比喻本身吗？（若需要则换更生活化的）
- 比喻与被比喻物的映射关系够清晰吗？（每条映射都能说出"X 对应 Y 的哪个部分"）
- 比喻有误导性吗？（会不会让用户在未被指出的方面做出错误推断？）

三项中任何一项不合格则换比喻。

### 要求五：讲解知识，会包含但不限于工具的实现原理、工作流程及其如何应用

讲解任何知识主题时（除非用户明确指定只讲某一维度），必须覆盖以下三个核心维度，**同等重要、不可偏废**。下文"知识类型调优策略"虽然给出不同维度的篇幅侧重建议，但三个维度都必须讲——侧重不等于省略。

#### 维度一：实现原理——讲透"为什么"

| 子维度 | 要求 | 示例（讲 HashMap） |
|--------|------|-------------------|
| **本质追问** | 解释核心设计思想和根本权衡 | "为什么用数组+链表/红黑树？因为数组寻址 O(1) 但扩容成本高——哈希冲突与空间浪费之间要权衡。" |
| **内部机制** | 解释核心工作机制，非表面用法 | 不是"存键值对"，而是"hash()→index→链表→树化→resize"的完整链路 |
| **理论支撑** | 有数学/理论基础时必须给出清晰解释 | 装填因子 0.75 的来源（泊松分布推导）、扩容的均摊分析 |
| **源码映射** | 指引关键源码的数据结构和关键方法 | HashMap.put() → hash() → putVal() → resize() 的调用链 |
| **演进历史** | 说明发展历程和每次改进的原因 | JDK 1.7 头插法 → 1.8 尾插法（防止死循环）、链表→红黑树（防 Hash 碰撞攻击） |

#### 维度二：工作流程——讲清"怎么做"

- **步骤化**：将流程拆分为步骤序列，每步注明 **「输入→处理→输出」**。
- **全生命周期**：从初始化/启动到执行核心过程，到结束/销毁/清理，时间顺序不可颠倒。
- **状态转换**：若涉及状态变化（TCP 状态机、线程生命周期），给出完整状态图及各状态含义。
- **异常路径**：除正常流程外，必须说明出错/超时/重试/回滚等异常路径。**异常路径和正常路径同等重要。**
- **数据流**：数据从哪来、经过什么转换、最终到哪去。

#### 维度三：如何应用——教会"怎么用"

| 子维度 | 要求 |
|--------|------|
| **环境准备** | 安装、配置、依赖、版本选择 |
| **典型场景** | 3-5 个最典型场景，每个说明"为什么适合用这个"而非"能用" |
| **最佳实践** | 推荐的项目结构、配置规范、命名约定、错误处理模式 |
| **实战示例** | 至少 1 个完整可复现的从零到一示例（全部代码+配置+命令+预期输出） |
| **集成生态** | 如何与上下游工具配合（如 Spring+MyBatis、Docker+K8s） |
| **常见陷阱** | 新手踩坑清单，每一条说明"为什么是坑"+"如何避免" |
| **性能考量** | N+1 查询、内存泄漏、并发瓶颈、慢查询——常见性能问题及定位方法 |
| **调试排错** | 常见错误排查思路、日志分析方法、推荐调试工具 |

步骤 1 ── 按主题自然开场（阶段 0）

### 要求七：每个要求都要高质量落实，不能减轻任务量

#### 质量等同原则

无论讲解的主题是"什么是变量"还是"Kubernetes 调度器源码分析"，无论一次讲一个知识点还是十个知识点，质量标准必须完全一致。禁止以下降级行为：

| 降级行为 | 正确做法 |
|---------|---------|
| "这个问题很简单，就不举例了" | 越简单的基础概念越需要例子（变量→"盒子装东西"） |
| "原理和上一题一样，不重复了" | 即使原理相同，也至少概括重申并指出具体差异 |
| "细节太多了，你去看文档吧" | 本 skill 直接提供详细内容——工作量不可转移给用户 |
| "时间有限，这次先不讲应用" | 除非用户明确同意裁剪某维度，否则三个维度全部覆盖 |

#### 深度与广度平衡

- **广度**：三个维度（原理/流程/应用）全部覆盖，不可因内容多而砍掉某一整个维度。
- **深度**：每个维度下的子条目不跳项。
- **冲突时**：优先保证深度（每点讲透），再补充广度（告知用户哪些维度本次未覆盖、后续可展开）。

#### 最终质量复核

在阶段 3（自我质量复核）中，从用户视角执行 4 项复核，并在同次复核中完成上文的一次表达检查。**4 项全部通过方可进入阶段 4（内部核验）**：

| 复核项 | 通过标准 |
|--------|---------|
| ①可理解性 | 一个对该领域陌生的读者能看懂 80% 以上吗？ |
| ②完整性 | 该主题的重要方面都涉及了吗？有没有明显的遗漏？ |
| ③准确性 | 全部内容是否事实正确、逻辑自洽？有无已知错误未修正？ |
| ④实用性 | 用户学完后能独立使用该知识解决实际问题吗？ |

## PDF/Word 文件内容概括整合模式

本 skill 支持将用户提供的 PDF 或 Word 文件中的全部内容进行**概括整合**，以 markdown 文件形式输出。此模式下，上述 7 条要求仍全部适用，且额外增加文件概括整合相关的专项规则。

本模式必须同时满足以下三条核心要求（逐句落实、不可遗漏）：

> **要求一**：对文件的内容进行一次稍微简略的概括，但是要包含到文件的每一句话。
>
> **要求二**：用户可能会有需求，根据用户的需求，进行不同程度的概括整合。
>
> **要求三**：以 md 文件的形式输出给用户。

### 三条核心要求的落实方案

#### 要求一：稍微简略的概括，但要包含每一句话

输出不是全文逐字照搬，而是在保持原文全部信息的前提下进行一次**稍微简略的概括性整合**。

| 维度 | 操作 | 示例 |
|------|------|------|
| **句句覆盖** | 原文中的每一句话都必须在输出中有对应表述。可以整合相邻的同主题句子，但不能跳过任何一句话。 | 原文三句"春眠不觉晓。处处闻啼鸟。夜来风雨声。" → 整合为"春眠不觉晓的清晨，处处可闻鸟啼，昨夜的风雨声令人感慨。"（三句信息全部保留，但合并为更简洁的表述） |
| **适当精简** | 去除冗余修饰词、重复表述、啰嗦的举例铺垫，保留核心信息。 | "正如我们前面所讨论过的，实际上这个问题可以这样来理解" → "这个问题的理解方式是" |
| **保留完整信息** | 数字、日期、名称、术语、定义、结论必须完整保留，不可因概括而丢失。 | "2024 年 3 月 15 日发布的 2.3.1 版本" → 不可简化为"近期版本" |
| **保留原文语气** | 若原文是正式语气则输出正式，若原文是口语/议论则保留该风格。 | — |
| **保留结构标识** | 章节编号（1.1、1.2）、列表编号、图表编号必须完整保留。 | — |

**逐句门禁（内部执行，以下格式不进入交付正文）**：草稿完成后，将原文逐句拆出，与输出逐句对照。每一句都必须在输出中找到对应的表达。对照表格式：

```
| 原文句 | 输出中对应位置 | 状态 |
|--------|---------------|------|
| "第一句……" | 第 2 段第 1 句 | ✓ |
| "第二句……" | 第 3 段第 2 句 | ✓ |
```

**覆盖率必须达到 100%**，即原文每一句都在输出中有对应。发现遗漏立即补充。

#### 要求二：根据用户需求，进行不同程度的概括整合

用户指定级别时遵从；未指定时使用 L2（适中）并简短说明，不等待确认。仅当用途或篇幅要求与 L2 明显冲突且无法从材料推断时询问。

**四级概括程度**：

| 级别 | 名称 | 输出风格 | 篇幅比例（相对原文） | 适用场景 |
|------|------|---------|-------------------|---------|
| **L1** | 详细整合 | 接近原文完整度，仅做轻微的措辞优化和冗余去除。每个论点、论据、数据点都独立保留。 | ~80% | 用户需要完整参考内容，用于后续分析或引用 |
| **L2** | 适中概括 | 合并同主题的相邻句子，去除重复表述和啰嗦铺垫，保留全部核心信息。段落层次清晰，重点突出。 | ~50%-60% | 用户需要理解全部内容但不需要逐字原文（**默认级别**） |
| **L3** | 精简概括 | 每个段落整合为 1-2 句话，保留全部关键结论、数据、定义、术语。省略论证过程、例子细节和过渡性语句（但每个句子代表的核心信息仍须纳入）。 | ~25%-35% | 用户需要快速掌握文件核心要点 |
| **L4** | 摘要级 | 按章节输出摘要，每个章节 1-3 句话。保留全部一级结论、定义、核心数据。省略绝大部分论证过程和例子。**仍须覆盖到每个句子所表达的核心含义**（不能跳过一个句子代表的完整信息）。 | ~10%-15% | 用户只需要文件的整体轮廓 |

篇幅比例和句数是选级参考，不是删字指标；发生冲突时以该级别应保留的信息、逐句覆盖及必要逻辑关系为准，不强行压到比例内。

**同级别内一致性**：整篇文件使用同一概括级别，不得前半部分 L1、后半部分 L3。

**级别切换**：输出完成后，用户可要求切换到另一级别重新输出。AI 须以完全相同质量标准的流程重新处理。

#### 要求三：以 md 文件的形式输出给用户

输出的 markdown 文件必须遵循以下规范：

```

### 完整的处理流程

收到文件后，严格按以下 7 步流程执行：

```

        ▼

### 文件类型处理技术方案

#### PDF 文件

| 场景 | 工具/方法 | 命令 |
|------|----------|------|
| **文本型 PDF**（可选词） | `read` 工具直接读取 + Python `PyMuPDF` | `python -c "import fitz; doc=fitz.open('文件.pdf'); print(doc[页码].get_text())"` |
| **扫描型 PDF**（图片扫描件） | 告知用户：扫描版 PDF 无法直接提取文本，需 OCR 工具预处理 | — |
| **表格密集 PDF** | 优先用 `pdfplumber` | `python -c "import pdfplumber; pdf=pdfplumber.open('文件.pdf'); print(pdf.pages[0].extract_text())"` |
| **PDF 提取备用方案** | `pdftotext`（需安装 poppler） | `pdftotext 文件.pdf 输出.txt` |

**执行顺序**：先尝试 `read` 工具读取 PDF（因为 `read` 工具原生支持 PDF）。若 `read` 返回的内容不完整或格式混乱，则切换到 Python 方案。

#### Word 文件（.docx）

| 工具 | 命令 | 说明 |
|------|------|------|
| Python `python-docx` | `python -c "import docx; doc=docx.Document('文件.docx'); print('\n'.join([p.text for p in doc.paragraphs]))"` | 提取所有段落文本 |
| `python-docx` 表格提取 | `python -c "import docx; doc=docx.Document('文件.docx'); [print('|'+'|'.join([c.text for c in r.cells])+'|') for t in doc.tables for r in t.rows]"` | 提取所有表格内容为 markdown 格式 |

#### .doc 文件（旧版 Word）

**不支持直接读取**。告知用户：
> ".doc 格式（Word 97-2003）无法直接提取文本。请用 Word 打开后另存为 .docx 格式，或将内容复制到新文档中保存为 .docx。"

#### PPT 文件（.pptx）

| 场景 | 工具/方法 | 命令 |
|------|----------|------|
| **文本提取（全部幻灯片）** | Python `python-pptx` | `python -c "import pptx; prs=pptx.Presentation('文件.pptx'); print('\n'.join(['--- 幻灯片 '+str(i+1)+' ---\n'+''.join([p.text for p in slide.shapes if hasattr(p, 'text')]) for i, slide in enumerate(prs.slides)]))"` |
| **逐张幻灯片保留结构** | Python `python-pptx` 分幻灯片输出 | `python -c "import pptx; prs=pptx.Presentation('文件.pptx'); [print(f'--- 幻灯片 {i+1} ---\n标题: {slide.shapes.title.text if slide.shapes.title else \"(无标题)\"}') for i, slide in enumerate(prs.slides)]"` |
| **表格提取** | `python-pptx` 表格遍历 | `python -c "import pptx; prs=pptx.Presentation('文件.pptx'); [print('|'+'|'.join([c.text for c in r.cells])+'|') for slide in prs.slides for shape in slide.shapes if shape.has_table for r in shape.table.rows]"` |
| **幻灯片备注提取** | `python-pptx` notes_slide | `python -c "import pptx; prs=pptx.Presentation('文件.pptx'); [print(f'幻灯片 {i+1} 备注: {slide.notes_slide.notes_text_frame.text}' if slide.has_notes_slide else '') for i, slide in enumerate(prs.slides)]"` |

**提取顺序**：幻灯片标题 → 正文文本框 → 表格 → 备注。每张幻灯片以 `--- 幻灯片 N ---` 分隔，并保留幻灯片编号。

**注意事项**：
- `python-pptx` 提取的是文本框中的纯文本，不包含图片中的文字
- 图形/图表/SmartArt 中的文字可能无法提取（`python-pptx` 仅提取 `shape.has_text_frame` 的文本框）
- 提取后的文本默认为无格式纯文本（加粗/斜体/颜色丢失），此为 PPT 提取固有局限

#### .ppt 文件（旧版 PowerPoint）

**不支持直接读取**。告知用户：
> ".ppt 格式（PowerPoint 97-2003）无法直接提取文本。请用 PowerPoint 打开后另存为 .pptx 格式。"

#### 文件类型处理流程汇总

| 文件类型 | 扩展名 | 支持状态 | 处理工具 |
|---------|--------|---------|---------|
| PDF（文本型） | .pdf | ✅ 支持 | `read` + `PyMuPDF` / `pdfplumber` |
| PDF（扫描型） | .pdf | ⚠️ 仅告知 | 需 OCR 预处理 |
| Word 文档 | .docx | ✅ 支持 | `python-docx` |
| Word 旧版 | .doc | ❌ 不支持 | 提示转 .docx |
| PowerPoint | .pptx | ✅ 支持 | `python-pptx` |
| PowerPoint 旧版 | .ppt | ❌ 不支持 | 提示转 .pptx |

### 输出质量核验清单（步骤 7 专用）

在最终输出 md 文件之前，按“四种模式的具体落实”完成一次表达检查，再对改后的最终文字逐项执行以下 4 类检查。**全部通过方可进入步骤 8。**

#### ① 乱码检查

| 检查项 | 操作 | 通过标准 |
|--------|------|---------|
| **不可见字符** | 用 Python 扫描输出文本中是否包含 `\x00`-`\x08`、`\x0b`、`\x0c`、`\x0e`-`\x1f` 等控制字符 | 输出文本中无任何控制字符 |
| **非法 UTF-8 序列** | 检查是否有 `\ufffd`（REPLACEMENT CHARACTER）出现 | 无 `\ufffd` |
| **中文乱码** | 检查是否有中文文本中夹杂的不可读字符（如 `ç¨`、`æµ`、`çš` 等不连续的 Latin-1 字符） | 无中文乱码片段 |
| **PDF 提取遗留** | 检查是否有 PDF 提取时残留的换行拼接错误（如单词被断成两半："appli-cation"、"docu-ment"） | 无错误断词 |
| **符号乱码** | 检查全角/半角符号是否统一、引号是否成对 | 符号格式统一、引号成对出现 |

**发现问题后的处理**：
- 发现乱码 → 判定为**提取阶段错误** → 切换读取方案（如从 `read` 切到 `PyMuPDF`，或从 `PyMuPDF` 切到 `pdfplumber`）→ 重新走步骤 3-8
- 再次提取仍有乱码 → 在输出 md 的文件头部用 `> ⚠️ 该文件部分内容存在乱码，已尽最大努力提取` 标注，并在内部原句映射中标记乱码句为 `[提取异常]`；未解决前不能作为完整成品交付

#### ② 与原文一致性检查

| 检查项 | 操作 | 通过标准 |
|--------|------|---------|
| **数据一致性** | 核对原文与输出中的数字、日期、百分比、版本号是否完全一致 | 所有数据逐字符相同 |
| **名称一致性** | 核对人名、地名、产品名、专有名词的大小写和拼写 | 名称完全一致 |
| **术语一致性** | 核对专业术语是否被错误替换为同义词（如"时间复杂度"→"时间复杂性"） | 术语与原文完全一致 |
| **否定一致性** | 检查概括后的句子是否改变了原文的肯定/否定含义 | 原文说"不推荐"→输出不能说"推荐" |
| **程度一致性** | 检查概括后的程度词是否与原文一致（"必须"、"可以"、"建议"、"禁止"等） | 程度词与原文一致，不自行升级或降级 |
| **引用一致性** | 原文引用的文献编号、法律条款编号、标准编号是否完整保留 | 编号逐项对应 |

#### ③ 逻辑错误检查

| 检查项 | 操作 | 通过标准 |
|--------|------|---------|
| **因果颠倒** | 原文说"A 导致 B"，概括后是否变成了"B 导致 A" | 因果关系方向正确 |
| **前后矛盾** | 同一概念在文件不同位置是否有不一致的描述（如前文说"该算法复杂度 O(n)"后文说"与 n 无关"） | 全文逻辑自洽 |
| **指代不明** | 代词（这、那、它、其）的指代对象在概括后是否因删减上下文而变得模糊 | 每个代词都有明确的指代对象 |
| **分类错误** | 原文的分类关系（A 属于 B、X 包含 Y、M 和 N 互斥）在概括后是否被改变 | 分类关系与原文一致 |
| **时序颠倒** | 原文的时间顺序在概括后是否被错误调整（先 A 后 B → 概括成先 B 后 A） | 时间顺序与原文一致 |

#### ④ 低级错误检查

| 检查项 | 操作 | 通过标准 |
|--------|------|---------|
| **错别字** | 逐段检查是否有常见的错别字（的/地/得混用、在/再混用、的/地混用） | 无错别字 |
| **标点错误** | 检查是否有不匹配的引号、缺少句号、连续逗号、中英文标点混用 | 标点使用正确且统一 |
| **格式断裂** | 检查 markdown 标题后是否紧接内容、表格是否对齐、代码块是否有闭合 | 格式完整无断裂 |
| **编号跳序** | 检查章节编号、列表编号是否连续（1→2→3，不是 1→3→5） | 编号连续无跳序 |
| **表格错位** | 检查 markdown 表格的列数是否一致、单元格内容是否错位 | 每行列数相同、内容在正确的列 |
| **空段落** | 检查是否有连续的空行、多余的空白段落 | 无连续空行（最多一个空行分隔） |
| **URL 残留** | 检查输出中是否残留了提取工具的调试信息、路径痕迹 | 无与原文无关的 URL 或路径 |

#### 质量核验未通过的处理

- 任意一项未通过 → 定位到对应位置修正 → 从修正点开始重走步骤 5-8
- 修正完成后重新跑一遍全部 4 类检查 → 全部通过才继续
- 用户反馈质量问题时 → 记录问题类型 → 定位原文 → 修正后重新输出并告知用户修改了哪里

### 本模式下的 7 条要求适配

| 要求 | 在文件概括整合模式中的特殊含义 |
|------|---------------------------|
| **一（正确性）** | 概括不得改变原文事实含义。数据/日期/名称/术语/结论必须与原文一致。疑似原文错误用 `[原文如此]` 标注。不得在概括中引入原文没有的信息或推断。输出前执行乱码检查 + 一致性检查，确保无乱码、无数据错误、无术语误替换 |
| **二（全面易懂）** | 结构完整性 + 语言流畅性。原文的全部结构要素都要在 md 中映射。概括后的语言须自然流畅，不能出现生硬的拼接感 |
| **三（举例）** | 不额外举例。原文中的例子在概括中按 L1-L4 级别保留相应程度（L1 完整保留、L4 只保留例子的结论） |
| **四（比喻）** | 不额外使用比喻 |
| **五（原理/流程/应用）** | 不适用——输出的是文件概括整合，不是知识讲解 |
| **六（不遗漏）** | **最核心的要求**。三条要求逐句落实：①稍微简略的概括但要包含每一句话 ②按用户需求分级别 ③输出为 md 文件。逐句核验时先核验这三条，再核验原始 7 条 |
| **七（高质量）** | 每个文件/每个概括级别都以完全相同的质量处理。不得因"文件很长"而降低逐句覆盖率或跳过 4 类质量核验。级别切换后重新输出时，质量标准与首次完全相同。输出 md 文件前必须经过完整的 4 类质量核验，发现的问题修正后才能输出 |

### 输出后的用户交互

1. 告知用户 markdown 文件的保存路径和文件名。
2. 简短提供文件链接和采用的概括级别；句数、覆盖率等检查统计仅供内部核对。
3. 标明实际采用的概括级别；用户提出调整后再修订，不因等待反馈扣留完整产物。
4. 按已知格式要求交付；非关键偏好采用一致默认格式，不强制追加问答。
5. 交付前内部执行“三条核心要求 + 原始 7 条要求”的适用核验；发现问题先修正，不能把用户验收当作自检的前置条件。

### 文件概括整合模式的清理规则

清理是独立步骤，删除仍须用户确认。只在已批准的清理范围内执行下表；待批准文件保持原样，不影响已完成的文档交付，也不删除无关文件：

| 保留 | 删除 |
|------|------|
| 原始文件（用户提供，不修改） | 提取过程中产生的临时 `.txt` 文件 |
| 输出 `原文件名_概括整合.md` | Python 脚本输出的临时内容（如 `提取内容.txt`） |
| （用户明确要求保留的其他文件） | 备份/副本（如 `原文件_备份.docx`、`原文件_副本.pdf`） |
|  | 下载的附加资源（如 OCR 图片、切割页） |

**删除流程**：
1. AI 扫描当前目录，识别出全部中间/临时/垃圾文件
2. 列出删除清单，逐项展示给用户确认：
   ```
   即将删除以下文件：
   - 临时提取_20240720.txt
   - 原文件_备份.pdf
   - slide_images/
   是否确认删除？(Y/N)
   ```
3. 用户确认后执行删除
4. 用户拒绝删除的项跳过，仅删除已确认的项
5. 保护清单内的文件绝不删除：
   - 原始用户文件
   - AI 输出的 `.md` 文件
   - `.git/` 目录及 `.gitignore`

## 代码解释模式

本 skill 支持对用户提供的代码文件（或代码片段）进行**逐句解释**，从语法和逻辑两个维度展开，并说明每个模块的作用。此模式下，上述 7 条要求仍全部适用，且额外增加代码解释相关的专项规则。

本模式必须同时满足以下三条核心要求（逐句落实、不可遗漏）：

> **要求一**：从语法和逻辑两方面，一句一句解释代码。
>
> **要求二**：说出每个模块的作用。
>
> **要求三**：解释必须准确、不遗漏任何代码行。

### 代码解释的输出格式

每段代码解释须严格遵循以下结构化输出格式：

```
### 模块概述：[模块名]

**模块作用**：（用 1-3 句话说明该模块的整体功能和职责）

| 行号 | 代码 | 语法解释 | 逻辑解释 |
|------|------|---------|---------|
| 1 | `import numpy as np` | `import` 导入语句，`as` 起别名 | 导入 NumPy 库并命名为 np，用于后续数值计算 |
| 2 | `def train_model(X, y):` | `def` 定义函数，参数 X(特征), y(标签) | 定义模型训练函数，接收特征和标签作为输入 |
| ... | ... | ... | ... |
```

**行号说明**：行号为代码在文件中的实际行号。若代码片段不是完整文件，行号从片段所在行开始编号。

### 完整的处理流程

```
用户提供代码文件路径或粘贴代码
        │
        ▼
┌──────────────────────────────────┐

           ▼

### 逐句解释的详细规则

保持逐行表格，但不要求每行套“这行代码用于……从而实现……”的句壳。同类语法再次出现时简述写法，同时讲清本行的对象和变化；不能省掉语法列，也不能用“同上”代替该行作用。某行只是结构闭合或注释时如实说明，不硬造业务效果。

例如 `total += price`：语法列可写“增量赋值，将右侧值加到左侧变量”；若上下文确为累计金额，逻辑列可写“把当前商品价格加入累计金额”。两列分别回答写法与本行作用，不能只把“累加”换词重复。代码没有给出的业务含义不要推测。多行共同构成机制时，在表前后用连贯段落说明依赖，表内仍逐行对应。

#### 语法解释规则

语法解释回答"这段代码在语言层面是什么"，须覆盖以下要素（适用则写，不适用不写）：

| 要素 | 说明 | 示例 |
|------|------|------|
| **语句类型** | 声明/表达式/赋值/控制流/函数调用/类定义/装饰器/上下文管理器等 | "这是一个 `with` 上下文管理器语句" |
| **关键字** | 使用的编程语言关键字及其含义 | "`try` 开始异常捕获块" |
| **API / 函数签名** | 调用的函数/方法/构造函数的完整签名及参数含义 | "`pd.read_csv(filepath, encoding='utf-8')`：读取 CSV 文件，指定编码为 UTF-8" |
| **数据结构** | 涉及的变量类型、数据结构特征 | "变量 `data` 是一个 Pandas DataFrame" |
| **语法糖** | Python 等语言的简写形式说明 | "`a if cond else b` 是三元表达式，等价于 if-else 简写" |
| **特殊运算符** | 重载运算符、箭头函数、展开运算符等 | "`**kwargs` 用于接收不定长关键字参数" |

#### 逻辑解释规则

逻辑解释回答"这段代码在业务/算法层面做了什么"，须覆盖以下要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **行为描述** | 这段代码执行了什么操作 | "从 CSV 文件中读取训练数据并加载到内存" |
| **设计意图** | 解释代码和已知上下文支持的作用；推测须明确，不编造作者动机 | "使用 try-except 捕获文件不存在异常，避免程序崩溃" |
| **数据变化** | 输入→处理→输出的数据流转 | "原始字符串经过 strip() 去首尾空格，再 split() 拆分为列表" |
| **边界/异常处理** | 涉及了哪些边缘情况 | "当列表为空时返回 None，而不是继续执行后续逻辑" |
| **性能/复杂度** | 如果涉及算法，说明时间/空间复杂度 | "这里用哈希表（dict）将查找从 O(n) 降到 O(1)" |
| **与其他代码的关联** | 与前后代码的调用/数据关系 | "返回的结果将作为下一段 `process_data()` 的参数传入" |

### 模块划分与作用说明

#### 如何划分模块

按代码功能边界划分，典型划分方式：

| 模块类型 | 识别特征 | 示例模块名 |
|---------|---------|-----------|
| **导入区** | 文件头部的 `import` / `require` / `include` 语句 | 依赖导入 |
| **常量/配置** | 全局变量、配置字典、环境变量读取 | 全局配置 |
| **工具函数** | 独立的小函数，无副作用，可复用 | 工具函数 |
| **数据层** | 数据读取/清洗/预处理相关代码 | 数据处理 |
| **模型/核心逻辑** | 算法实现、核心业务逻辑 | 核心模型 |
| **可视化** | 绘图、图表生成相关代码 | 可视化 |
| **入口** | `if __name__ == '__main__'`、`main()` 等 | 程序入口 |

**补充规则**：
- 少于 10 行的极短代码 → 可不划分模块，直接逐句解释
- 单个函数超过 50 行 → 函数内部按逻辑块拆分子段落
- 模块命名要体现功能（"数据处理"好于"第二部分"）

#### 模块作用说明格式

```
**模块作用**：[一句话概括功能]

**输入**：[模块接收什么数据/参数]
**输出**：[模块产出了什么]
**调用的下游模块**：[该模块被谁使用]
```

### 本模式下的 7 条要求适配

| 要求 | 在代码解释模式中的特殊含义 |
|------|---------------------------|
| **一（正确性）** | 语法解释必须准确（如误将 `append` 说成"插入到头部"即违反本条）。逻辑解释必须符合代码实际行为，不得凭空推测代码意图。不确定的语法/逻辑用 `[待核实]` 标注 |
| **二（全面易懂）** | 代码解释表格的语法列和逻辑列必须每行都有内容（不允许空单元格）。语言须通俗，避免用"这个就是对数据进行处理"这类空洞描述 |
| **三（举例）** | 在解释 API/语法糖/设计模式时，可附简短的使用示例作为说明，以 `例如：` 标注在逻辑解释列末尾 |
| **四（比喻）** | 当代码涉及抽象概念（装饰器、生成器、闭包、指针等）时，用比喻辅助理解，放在逻辑解释列末尾，以 `比喻：` 标注 |
| **五（原理/流程/应用）** | 步骤 2（模块划分）对应"流程"，步骤 4（模块间关系）对应"原理"。不涉及"应用"维度 |
| **六（不遗漏）** | 每个非空代码行（含注释）都必须有解释。逐行核对原始行号与输出对应，允许空行造成行号间隔，不能漏掉实际代码或注释 |
| **七（高质量）** | 短代码（5 行）和长代码（500 行）都以相同精度解释。不得因代码长而跳过某些行或写"同上"敷衍 |

### 输出后的用户交互

1. 输出完整的代码解释结果（含模块概述 + 逐行解释表格 + 模块关系说明）
2. 直接交付学习内容：总代码行数、已解释行数、覆盖率百分比
3. 询问用户是否需要调整：
   - 是否需要更详细的语法解释
   - 是否需要更深入的设计原理/架构分析
   - 是否需要保存为 `.md` 文件
4. 完成请求范围和适用自检后交付；后续用户反馈进入修订，不作为本轮完成前提

如果解释过程中产生了临时文件（如从代码文件提取的中间 `.txt`），完成后参照文件概括整合模式的清理规则执行：中间文件经用户确认后删除；未批准时保留并单列待办，不阻塞已完成的解释交付。

## 算法题讲解模式

本 skill 支持对**算法题/编程竞赛题/面试手撕题**进行完整讲解。核心特点是：**给出代码的同时，必须把"建模思路"和"代码思路"两条线讲解清楚**——不是只贴代码+注释，而是让用户真正理解"为什么这样建模、为什么这样写"。

此模式下，上述 7 条要求仍全部适用，且额外增加算法题讲解相关的专项规则。

本模式必须同时满足以下三条核心要求（逐句落实、不可遗漏）：

> **要求一**：清晰讲解**建模思路**——把题目如何抽象成数学模型/数据结构/算法问题，以及为什么这样建模。
>
> **要求二**：清晰讲解**代码思路**——把建模方案翻译成代码的每一步编码逻辑，以及边界情况如何处理。
>
> **要求三**：给出**完整可运行的代码**，且代码与思路严格对应，不遗漏任何关键步骤。

### 算法题讲解的核心输出结构

以下内容均须覆盖，通常按此顺序展开；可按真实推导调整段落和标题，保持先定义后使用、先交代条件再得出结论。用户指定结构时遵从，不因调整表达省略建模、代码思路或自检：

```
【1. 题意理解与信息抽取】
    - 题目在问什么：输入是什么、输出是什么
    - 约束条件（数据范围）→ 推导复杂度上限
    - 边界情况清单（空输入、单元素、极端值）

【2. 建模思路】
    - 问题抽象：这个题本质是什么问题？（排序/搜索/DP/图/贪心...）
    - 关键观察：能发现什么规律/性质，让问题可以化简
    - 数据结构选择：为什么选这个数据结构
    - 算法设计：整体算法框架，核心状态转移/贪心策略/搜索策略
    - 复杂度分析：时间/空间复杂度，为什么达标

【3. 代码思路】
    - 编码结构规划：代码分几段，每段负责什么
    - 逐段实现逻辑：每段代码怎么写、为什么这么写
    - 关键细节：边界判断、状态初始化、索引处理、避免越界

【4. 完整代码】
    - 语言标注的完整可运行代码
    - 含必要的输入读取、主函数、预期输出

【5. 样例推演与正确性解释】
    - 用 1-2 个手算例子走一遍代码逻辑
    - 检查边界情况是否都被处理
    - 检查是否与建模思路一致
```

### 建模思路的详细要求

建模是算法题的核心，也是多数人最欠缺的能力。建模思路必须回答"为什么这么建模"，而非只陈述结论。

#### 5 步建模流程

下表用于检查思考是否完整，不要求每题逐字套用五个标题。“找冗余”“数据换时间”只有在当前算法确实如此时才按此叙述；其他题目应解释实际的数学性质或求解依据，不虚构优化过程。朴素做法已足够时说明理由，不编造更优解。所用方法的必要推导、选择依据和边界仍须完整。

| 步骤 | 内容 | 示例（"两数之和"） |
|------|------|-------------------|
| **① 题型识别** | 判定这是哪类问题（线性扫描/双指针/二分/DP/贪心/图/数学/数据结构题） | 属于"查找匹配对"问题 |
| **② 暴力先想** | 先想最朴素的做法（通常 O(n²)/暴力枚举），作为正确性参照 | 双层循环枚举所有 i<j，检查 a[i]+a[j]==target |
| **③ 找冗余** | 分析暴力做法里哪些重复计算/冗余查找可以优化 | 内层循环每次都在"找补数"，查找是 O(n) 的冗余 |
| **④ 数据换时间** | 用什么数据结构把冗余查找降到 O(1)/O(logn) | 用哈希表存"值→下标"，补数查找 O(1) |
| **⑤ 定算法框架** | 确定最终算法，写出核心逻辑一句话 | 一次遍历，边查哈希表边插入 |

**建模的每个选择都必须给理由**：
- 为什么选这个数据结构？（哈希 O(1) 查找 vs 数组 O(n) 查找）
- 为什么这个状态定义是合理的？（DP 状态的后效性检查）
- 为什么这个贪心策略正确？（需要证明或直觉+反例测试）

#### 建模角度自查

| 检查项 | 说明 |
|--------|------|
| 是否识别出题型 | 能说出"这是 DP/双指针/二分..." |
| 是否解释了选择理由 | 每个数据结构/算法选择都有"为什么" |
| 是否交代朴素做法与选择依据 | 有优化时说明改进来自哪里；无需优化时说明朴素做法为何满足约束 |
| 是否分析了复杂度 | 时间/空间复杂度推导清楚，与数据范围匹配 |
| 是否考虑边界 | 空输入、极端值、重复元素等是否纳入建模 |

### 代码思路的详细要求

代码思路是把"数学模型"翻译成"代码逻辑"的桥梁，必须逐段讲清楚。

#### 代码分段的讲解方式

将代码按功能划分为若干逻辑段（通常是 3-6 段），以下格式用于确认内容齐全，可写成衔接自然的段落：

```
**代码段 N：[段落名]**

- **这段做什么**：本段代码的整体职责
- **逐行/逐块逻辑**：关键行的作用与为什么
  - 第 X 行 `...`：作用...（为什么这样写）
  - 第 Y 行 `...`：作用...（边界处理，因为...）
- **进入下段的条件**：这段执行完后，什么情况下进入下一段
```

#### 代码思路要点

| 要点 | 要求 | 示例 |
|------|------|------|
| **从建模到代码的映射** | 明确说出每段代码对应建模的哪一步 | "这一段就是建模中的'边查边插'，对应第④步" |
| **边界处理显式化** | 每个边界判断都要解释"防什么" | "这里 `if not nums: return []` 是防空数组越界" |
| **索引/指针细节** | 双指针、DP 数组下标、循环边界的来龙去脉 | "`right = len(nums)-1` 因为数组下标从 0 开始" |
| **状态初始化理由** | DP 初始值、哈希初始内容为什么这样设 | "`dp[0]=0` 表示长度为 0 的前缀和" |
| **与暴力对比的落地** | 说明优化体现在代码的哪一行 | "原来的 O(n) 查找变成了哈希表查询，体现在第 X 行" |

### 完整代码的输出要求

1. **语言标注**：代码块使用 ` ```cpp` / ` ```python` 等标注语言
2. **完整可运行**：含必要的 import/头文件、输入读取、main/入口函数、输出
3. **关键行注释**：在复杂度关键点、边界处理点、状态转移点加简短注释（中文）
4. **与思路对应**：代码中的核心变量名与建模思路中的概念保持一致，方便对照
5. **复杂度标注**：在代码前或后明确标注时间/空间复杂度

### 正确性自检要求

代码草稿完成后，必须在内部执行以下自检（不可省略），修正问题并复核后再交付代码和讲解。表中检查项及通过状态不进入输出；有教学价值的推演与证明按知识内容呈现：

| 自检项 | 做法 |
|--------|------|
| **样例走查** | 用题目的示例输入手算走一遍代码逻辑，确认输出正确 |
| **边界走查** | 空输入、单元素、最大/最小值的处理是否正确 |
| **复杂度复检** | 与数据范围对照，确认不会超时/超内存 |
| **思路一致性** | 代码行为与建模思路描述是否一致，有无"思路说 A 代码写 B" |
| **常见陷阱** | 是否踩了这类题的常见坑（溢出、负数下标、重复元素、排序稳定性等） |

### 算法题讲解的完整处理流程

```
用户提供算法题（题目描述/链接/代码要求）
        │
        ▼
┌──────────────────────────────────┐
│ 步骤 1：题意解析                  │
│   提取输入/输出/约束/数据范围     │
│   列出边界情况                   │
└──────────┬───────────────────────┘
           ▼
┌──────────────────────────────────┐
│ 步骤 2：建模思路讲解              │
│   题型识别 → 暴力先想 → 找冗余    │
│   → 核对实际优化依据 → 定算法框架 │
│   每个选择给理由，复杂度分析       │
└──────────┬───────────────────────┘
           ▼
┌──────────────────────────────────┐
│ 步骤 3：代码思路讲解              │
│   编码结构规划 → 逐段实现逻辑     │
│   → 边界处理 → 与建模一一对应     │
└──────────┬───────────────────────┘
           ▼

### 多解法讲解（进阶）

当题目有多种解法时，按以下原则讲解（用户未要求时至少给出最优解 + 一种对照解）：

| 情形 | 做法 |
|------|------|
| **暴力解 vs 最优解** | 两种都给：暴力解作为"为什么需要优化"的对照，重点讲从暴力到最优的演进 |
| **两种最优解**（如 DP 和贪心都能做） | 两种都给：说明各自适用边界和选择的判断依据 |
| **用户要求特定解法** | 按用户要求重点讲，同时简述其他可行解 |

每种解法的讲解都必须走完整的"建模思路→代码思路→代码→自检"流程，不可因是第二种解法而简化。

### 算法题模式下的 7 条要求适配

| 要求 | 在算法题讲解模式中的特殊含义 |
|------|---------------------------|
| **一（正确性）** | 建模必须正确（如 DP 状态转移方程、贪心策略必须正确）。代码必须与思路一致且可运行。复杂度分析必须准确。复杂度标注与数据范围匹配 |
| **二（全面易懂）** | 建模思路和代码思路必须都讲清楚，缺一即不完整。术语（如"状态转移""双指针""单调栈"）首次出现给出解释。结构按真实推导组织（五项建模检查、分段代码思路） |
| **三（举例）** | 每个难点（状态转移、边界处理、指针移动条件）至少 1 个例子，优先用手算小规模输入演示 |
| **四（比喻）** | 讲解算法思想/数据结构时可用比喻（如"双指针像两个人在赛跑""单调栈像排队时后面的人比前面矮就出队"） |
| **五（原理/流程/应用）** | 建模思路对应"原理"，代码思路对应"流程"，复杂度与扩展对应"应用"。三者都须覆盖 |
| **六（不遗漏）** | 建模检查各项按实际适用性落实，不为套五步虚构过程；代码分段讲解不可漏段，正确性自检不可省略 |
| **七（高质量）** | 简单题（两数之和）和难题（DP/图论）都以相同质量讲解。不得因题简单而省略建模思路直接贴代码 |

### 算法题讲解模式的完成标准

- [ ] 题意已解析（输入/输出/约束/边界）
- [ ] 建模思路已讲解（五项检查已按实际适用性落实，必要理由和推导完整）
- [ ] 同次表达检查已完成：方法选择有据，推导依赖完整，无虚构试错和重复套话
- [ ] 建模每个选择都有理由
- [ ] 复杂度分析已完成且与数据范围匹配
- [ ] 代码思路已讲解（代码已分段，每段逻辑清楚）
- [ ] 边界处理已显式说明（每个判断解释"防什么"）
- [ ] 代码与建模思路一一对应
- [ ] 完整代码已给出（语言标注/可运行/关键注释/复杂度标注）
- [ ] 正确性自检已执行（样例走查/边界走查/复杂度复检）
- [ ] 7 条要求已逐条核验

### 算法题讲解模式的用户交互

1. 内部自检并修正后输出完整讲解（题意→建模→代码思路→代码→有教学价值的样例推演与正确性解释）
2. 完整请求直接交付；仅在用户选择分步教学时询问是否理解建模思路
3. 提供进阶选项：

   - 是否需要另一种解法

   - 是否需要把讲解保存为 .md 文件
4. 完成请求范围和适用自检后交付；后续用户反馈进入修订，不作为本轮完成前提

## 按知识类型调优策略

不同类型知识的讲解重心略有不同。以下为补充指南，**不可替代要求一至要求七**。注意：三个维度（原理/流程/应用）都须覆盖，下表仅提供**篇幅侧重和先后顺序**参考，不按百分比裁剪必要解释，也不等于省略任何维度。

| 知识类型 | 示例 | 篇幅分配 | 讲解顺序建议 |
|---------|------|---------|-------------|
| **概念/理论** | 什么是 REST、CAP 定理 | 原理 50% 流程 20% 应用 30% | 概念→原理→应用→(简要)流程 |
| **工具/框架** | Docker、React、Spring | 原理 25% 流程 25% 应用 50% | 比喻引入→应用→原理→流程；比喻必须给 |
| **语言特性** | 闭包、泛型、协程 | 原理 40% 流程 20% 应用 40% | 概念→原理→应用→流程 |
| **算法/数据结构** | 快速排序、红黑树 | 原理 40% 流程 40% 应用 20% | 概念→原理(理论支撑)→流程(步骤+数据流)→应用 |
| **协议/规范** | HTTP、TCP/IP | 原理 30% 流程 50% 应用 20% | 概念→流程(状态转换+异常路径)→原理(设计权衡)→应用 |
| **设计模式/架构** | 观察者模式、微服务 | 原理 35% 流程 25% 应用 40% | 本质追问→应用场景→原理→流程 |

## 多轮对话衔接规则

用户可能在一次讲解中多次追问。衔接规则：

1. **上下文保留**：每次追问默认基于上一轮讲解的全部内容。不需要重复已讲内容，但引用时须指明引用位置（如"刚才讲 HashMap 的扩容机制时提到……"）。
2. **追问即缩小范围**：用户的追问通常是一个子话题，此时切换到该子话题的完整流程（原理/流程/应用），而非只答追问本身。
3. **跨主题追问**：如果用户问的是与当前主题不同的新知识，视为新的一次完整讲解，重新执行全流程。
4. **质量不衰减**：第 5 轮追问的质量标准与第 1 轮完全相同。**不得因对话轮次增多而简化例子、省略比喻或跳过核验。**
5. **累计时长提醒**：若累计讲解超过 30 分钟或 5 个完整子主题，可在自然停顿处询问是否需要阶段性总结；不阻塞当前已授权交付。

## "不知道"的处理策略

当用户提出的问题超出本 skill 的能力范围时：

1. **明确告知**："这个问题超出了我能确认的知识范围，我无法给出可靠的讲解。"
2. **区分类型**：
   - **超出知识范围**（如未公开的内部技术）：告知用户并建议官方渠道。
   - **信息过时**（如已废弃的 API）：告知用户"我掌握的信息可能已过时，建议查阅最新文档"。
   - **需要实时数据**（如最新版本号）："这需要实时查询，我建议你访问[官网]获取最新信息。"
3. **提供替代路径**：即使不能直接回答，也提供接近或相关的知识点建议。
4. **不可编造**：**在任何情况下都不得编造答案。** 宁可不说，不可胡说。

## 核心纪律

1. **正确性第一**：发现输出中有错误或疑似的错误内容，立即停止输出，核实修正后再继续。**宁可不出，不可错出。**
2. **用户理解优先**：用户不理解时重复用不同角度解释，分步教学时等待用户理解反馈；完整讲解则补充解释后继续完成剩余范围。切换角度时明确说"我从另一个角度再解释一次"。
3. **不猜测**：不确定的内容标注 **「待核实」** + 原因，不隐瞒不模糊。**确定就是确定，不确定就是不确定。**
4. **无不讲原则**：无论多基础的"简单"概念（变量、函数、循环），都要以完整质量流程讲解——例子、比喻、原理、流程、应用一个不落。**越基础的概念越需要比喻，因为新手还没有建立该领域的直觉。**
5. **每一条都可审计**：讲解完成后必须逐条核验**全部 7 条要求**的每一条子条目（内部执行，用于查漏补缺）。核验照常进行不可省略，但其结果**不向用户输出核验表格**——只用于内部修正。
6. **不编造**：超出能力范围时按"不知道"处理策略执行，不得编造答案。

## 质量门禁——以下任何一条触发即不可结项

| 禁止行为 | 原因 |
|---------|------|
| "详情请参考官方文档"代替详细讲解 | 工作量转移给用户 |
| 关键事实未核验就输出 | 违反要求一 |
| 抽象概念无例子 | 违反要求三 |
| 工具/组件无比喻 | 违反要求四 |
| 只讲用法不讲原理，或只讲原理不讲应用 | 三个维度缺一违反要求五 |
| 内部核验未执行（跳过逐条对照检查） | 违反要求六 |
| 用户表示不理解时回复"已在上面讲过" | 违反要求二 |
| 不确定的内容以确定口吻输出 | 违反要求一 |
| 跳过任何一条规则的任何子条目 | 违反要求六 |
| 因"内容简单"而减少例子或比喻 | 违反要求七 |
| 编造答案 | 违反核心纪律第 6 条 |
| 概括整合中遗漏原文句子 | 违反逐句门禁——覆盖率必须 100% |
| 概括时改变原文事实含义（数据/日期/结论等） | 违反要求一——概括不得改变原意 |
| 忽略用户指定的概括级别 | 违反要求二；未指定时应直接采用 L2 |
| 同一文件中混用不同概括级别 | 违反同级别一致性原则 |
| 输出 md 文件包含乱码（未做乱码检查） | 违反输出质量核验——步骤 7 ① 乱码检查 |
| 输出 md 文件与原文数据不一致（数字/日期/版本号） | 违反输出质量核验——步骤 7 ② 一致性检查 |
| 输出 md 文件存在逻辑错误（因果颠倒/前后矛盾） | 违反输出质量核验——步骤 7 ③ 逻辑检查 |
| 输出 md 文件包含错别字/标点混用/表格错位 | 违反输出质量核验——步骤 7 ④ 低级错误检查 |
| 遇到 .doc 格式不提示用户转换 | 违反处理流程——需告知用户转换 |
| PDF 提取不完整不告知用户改用 Python 方案 | 违反处理流程——`read` 提取不完整时应切换方案 |
| 未在内部核对原句与输出的对应关系 | 违反要求一——未完成逐句覆盖检查 |
| 学习正文、对话或默认附件包含检查项通过表或同类报告 | 违反输出纯净性；检查在内部完成，仅交付学习内容 |
| 润色后丢失条件、逐句/逐行对应或证据归属 | 违反自然表达保真要求；修正该处并复核受影响内容，不另跑整篇风格改写 |
| 未执行 4 类质量核验就直接输出 md 文件 | 违反步骤 7——质量核验不可跳过 |
| 未清理中间文件/垃圾文件 | 违反步骤 9——完成后只保留原始文件 + 输出 .md |
| 删除保护清单内文件（原始文件/输出 .md） | 违反步骤 9——保护清单内文件绝不删除 |
| 清理前未列出清单供用户确认 | 违反步骤 9——删除前必须逐项确认 |
| 代码解释中遗漏代码行（跳过不解释） | 违反代码解释要求一——每行代码都须解释 |
| 语法解释存在事实错误（API/关键字/参数说错） | 违反要求一——语法必须准确 |
| 逻辑解释与代码实际行为不符 | 违反要求一——逻辑必须与代码一致 |
| 表格中语法列或逻辑列为空 | 违反七（高质量）——不能有空单元格 |
| 未划分模块或未说明模块作用 | 违反代码解释要求二——必须说明每个模块的作用 |
| 模块间关系未说明 | 违反步骤 4——模块间关系须说明 |
| 算法题只给代码不讲建模思路 | 违反算法题要求一——建模思路必须讲清楚 |
| 算法题只给代码不讲代码思路 | 违反算法题要求二——代码思路必须逐段讲清楚 |
| 建模思路缺少理由（只给结论不给为什么） | 违反算法题要求一——建模每个选择都要给理由 |
| 代码与建模思路不一致（思路说 A 代码写 B） | 违反算法题要求二——代码必须与思路对应 |
| 算法题未分析复杂度或复杂度错误 | 违反算法题要求一——复杂度分析必须准确 |
| 未做正确性自检（样例走查/边界走查） | 违反算法题要求三——自检不可省略 |
| 因题目简单而省略建模思路直接贴代码 | 违反七（高质量）——简单题同样需要完整讲解 |

## 快速参考卡片

| 要求 | 一句话记忆 | 最关键的 1 个动作 |
|------|-----------|-----------------|
| 一（正确性） | 宁可不出，不可错出 | 输出前做事实交叉核验 |
| 二（全面易懂） | 8 维覆盖 + 7 条写作规范 | 概览先行；分步教学才逐主题等待反馈 |
| 三（举例） | 每难点有具体演示 | 识别 5 类难点信号，按当前难点选择例子 |
| 四（比喻） | 每工具至少 1 喻 | 找准核心职责 + 指出比喻局限，核对比喻的实际映射 |
| 五（原理/流程/应用） | 三个维度都讲，侧重可不同 | 每个维度逐项对照子维度清单 |
| 六（不遗漏） | 逐句检查，一句不漏 | 在内部逐一对照规则原文，对每个子条目打 ✓ |
| 七（高质量） | 不因简单而减量 | 执行 4 项质量复核后才可结项（核验仅内部留存，不输出报告） |
| **文件概括（要求一）** | 稍微简略的概括，但包含每一句话 | 原文逐句编号 → 输出逐句对照 → 覆盖率 100% |
| **文件概括（要求二）** | 按用户需求分四级概括 | 优先采用指定级别，否则默认 L2；同级一致 |
| **文件概括（要求三）** | 输出为 md 文件 | 保存为 `原文件名_概括整合.md` |
| **文件概括（质量核验）** | 4 类检查通过后才输出 | 乱码检查 → 一致性检查 → 逻辑检查 → 低级错误检查 |
| **文件概括（清理）** | 完成后只保留原始文件 + 输出 .md | 列出清单 → 用户确认 → 删除中间文件 |
| **代码解释（核心）** | 语法 + 逻辑双维度逐句解释 | 行号表格 → 语法列 + 逻辑列 → 每行有内容 |
| **代码解释（模块）** | 按功能划分模块并说明作用 | 模块划分 → 模块作用概述 → 模块间关系 |
| **算法题（建模思路）** | 把题抽象成什么，为什么这么建模 | 按实际方法完成五项建模检查，讲清选择依据，不套用虚构优化过程 |
| **算法题（代码思路）** | 建模怎么翻译成代码 | 代码分段 → 每段讲"做什么+为什么"→ 边界显式化 |
| **算法题（完整代码）** | 可运行代码 + 自检 | 语言标注 + 关键注释 + 样例/边界走查 |
