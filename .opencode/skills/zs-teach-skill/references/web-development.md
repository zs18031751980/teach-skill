# Web 开发讲解的针对性指导

按主技能确定范围。解释技术不等于授权搭建、部署网站；实际开发任务遵循用户另行给定的范围。框架和 API 行为涉及版本时查对应官方资料，不把一个框架的机制当作整个 Web 的规则。

## 从一次交互追踪机制

按当前疑点沿实际链路解释：用户操作、事件处理、状态变化、请求、服务端处理、响应以及界面更新。明确代码在哪里执行、哪一端持有状态、数据怎样经过接口；只展开与本次问题相关的环节，不每次从 DNS 讲起。

## 用现象定位层次

教学示例同时说明预期画面或响应，以及能观察该过程的位置，如 Network、Console 或服务端日志。故障讲解先依据症状和证据缩小范围，不连续给用户一串互不相干的配置修改。

例如 `fetch` 收到 HTTP 404 时通常仍得到 Response，而非仅因 404 自动进入 Promise 的拒绝分支；需要检查状态或 `response.ok`，再决定如何显示错误。网络失败与响应正文解析失败是不同阶段的问题。[MDN Fetch 指南](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

跨域问题说明浏览器的响应访问限制与服务端配置关系；不能把 `no-cors` 说成让前端任意读取跨域响应的修复。只解释当前请求需要的规则，不默认引入认证系统设计。

## 保持示例可理解

提供代码时交代必要文件位置、运行前提和可见结果，避免用大量脚手架盖住核心机制。交互教学涉及相关状态时，说明加载、空结果或失败反馈；表单与页面结构按需要讲标签、键盘操作和语义。它们不是每个语法问答的固定附加任务。

同次内部复核关注执行环境、数据/状态流、观察结果和版本前提是否一致，不把“构建成功”当作界面行为已经验证。

## 按前后端问题定位讲解层次

按用户实际卡点选择下列子主题。每段中的输入和数字均为教学条件；换到用户材料时重新核对，不能把示例答案直接套用。只输出当前问题所需的解释，不照搬本文件的备课结构。

### HTML 与表单

卡点是“输入框有值为何请求里没有”，在原生 FormData(form) 场景检查 name、disabled 与控件类型：只有 id、没有 name 的输入不会因此自动成为提交字段；disabled 字段也不纳入。先展示表单中的值与实际请求字段，再解释语义。[MDN FormData](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_FormData_Objects)

若问标签关联，区分 label 的 for/id 关联与提交字段 name；若问受控表单，则说明框架提交逻辑，不能把原生提交规则直接当作自定义请求构造的全部规则。

### CSS 布局

卡点是“width=200px 为什么还变宽”，用无其他尺寸约束的普通块：content-box、左右 padding 各 20px、border 各 2px，边框盒宽为 244px；同条件改为 border-box 后指定宽 200px 包含这些内边距和边框。说明 margin 不包含在这两个宽度定义内。[MDN box-sizing](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/box-sizing)

若是 flex 收缩、grid 轨道或定位问题，应转而检查各自约束与包含块；不要将盒模型例子当作所有尺寸异常的解释，更不要默认用 !important 覆盖。

### JavaScript 执行

卡点是日志顺序时，限定同一次浏览器脚本执行：依次记录 A、注册 setTimeout 输出 T、注册已解决 Promise 的 then 输出 P、记录 B，会先看到 A、B，再 P、T。按注册和执行位置解释调用栈与队列，定时器不是睡眠该脚本。

若回调取到了旧值，则追踪闭包引用或框架状态快照，而不是继续背事件循环；若代码运行在其他宿主中，查该宿主调度规则。依据见下文执行模型来源。

### 组件状态

卡点是连续更新只加一次时，可使用明确的 React 示例：同一事件中以旧快照 count=0 连续调用两次 setCount(count+1)，均提交值 1；两次纯函数式更新 setCount(c=>c+1) 则顺着待处理状态得到 2。不要推广到所有框架。[React 状态更新队列](https://react.dev/learn/queueing-a-series-of-state-updates)

若问父子状态同步，先定位唯一的数据拥有者和更新入口；若问派生值，判断是否应从现有状态计算。不能一律建议增加更多状态或副作用来强迫刷新。

### 请求与错误

卡点是“404 为何没进入 catch”，沿 fetch 收到 Response、检查 response.ok、解析正文分阶段说明。对照 404 的有效 JSON 响应与 200 但正文不符合预期 JSON 的响应，解释 HTTP 失败和解析失败为何不是同一判断。

若是网络失败或取消，再说明拒绝来自请求过程；若 HTTP 与 JSON 都正常但业务码失败，解释接口契约和界面反馈。不能只添加一个 catch 后宣称所有错误已处理。

### 服务端接口

卡点是“页面禁用了按钮为何还会收到非法请求”，用直接发送 amount=-1 的请求说明前端交互限制不会约束其他客户端；服务端需按接口契约校验该值。若请求涉及某账户，还要区分登录身份与是否允许操作该账户。

若返回 401/403/校验错误，应查项目的实际错误契约再解释；若是 CORS，回到浏览器访问限制，不能把跨域设置当作鉴权修复。只涉及参数校验时不搭建整套权限系统。

### 缓存与数据刷新

卡点是“服务端改了，页面还旧”，追踪一次实际读取：组件是否用了已有状态、Network 是否发请求、响应是否仍旧、是否存在 HTTP 或服务端缓存。例：详情页用用户 ID 作缓存键，改成另一个 ID 却复用旧键，说明错误是键与数据身份不对应，而非简单“缓存有问题”。

若是更新后的失效策略，说明哪些消费者需要重新读取；若是 HTTP 缓存，联系实际缓存头。不要默认清空所有层缓存，也不把刷新页面当作解释。

### 渲染与路由

卡点是“直达某路径失败，站内点击却正常”，比较浏览器向服务器直接请求 /orders 与已加载页面内的路由切换。仅客户端路由的应用中，服务器可能没有该资源或回退规则；先定位实际架构，再说明相应配置。

若是 SSR 页面已有内容却暂时不能交互，区分服务器 HTML 与客户端接管交互；若是静态生成的数据新旧，追踪生成时点与更新机制。不能从路由名称推断页面一定在客户端或服务端渲染。

### 可访问性与响应式

卡点是“鼠标能点，键盘不行”，比较原生 button 与只注册点击事件的普通 div，实际沿 Tab 焦点和 Enter/Space 激活路径解释语义控件的作用，不只说“加 ARIA”。

若是小屏横向溢出，使用长文本、固定宽度和实际容器尺寸定位最小宽度约束；若是弹窗，追踪进入与退出后的焦点。选择贴合问题的一条操作路径，不仅缩小截图判断可用性。

### 构建与部署

卡点是“服务器环境变量改了，前端地址没变”，先辨明该值是构建时写入 bundle，还是应用运行时读取配置。前一种情况需更新相应产物，后一种需核对实际加载的配置；不假定每个框架都同样注入变量。

若是资源 404，查构建产物路径与部署基路径；若是本地可用上线失败，比较接口地址、协议和代理范围。向浏览器下发的内容不用于保存秘密，不能将改变量名前缀当成保密手段。

## 把异步问题变成可观察顺序

浏览器事件循环的教学可以用同步输出、已解决 Promise 的回调和定时器展示顺序，但要交代任务来源和运行环境，再解释为何发生。当前任务中的同步代码先完成；微任务在相应检查点处理；定时器延迟不代表回调能准时执行。[MDN JavaScript 执行模型](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)

不要只让用户背“微任务优先”：把回调何时加入队列、栈何时清空与输出位置对应起来。只有问题涉及具体框架调度时，才继续读该框架资料。

## 请求顺序与界面状态

搜索框连续发出 A、B 两个请求时，A 可能比 B 晚完成。若都直接写入同一结果状态，旧查询可能覆盖新查询。可按任务说明取消请求、请求标识或结果有效性判断解决的是哪个问题，不把“用了 await”当作避免竞争的保证。

对加载、成功、空结果与错误状态，沿实际界面行为说明；不要为了补齐状态表虚构产品需求。接口错误示例应同时交代用户能看到的反馈和开发者用于定位的证据，不能把堆栈原文当作用户提示。

## 代码与观察位置对应

给跨文件示例时，标明哪些代码属于浏览器、服务端或构建配置，以及必要的运行入口。修改一个关键变量或样式就能验证的例子，不创建完整项目。需要真实页面验证时，观察交互与网络行为，不以静态代码阅读代替实测。

用户反馈“没有变化”时，先查相关的状态、样式来源、请求或产物是否实际被使用，再解释修正；不默认推荐重装依赖、关闭安全限制或清空所有配置。
