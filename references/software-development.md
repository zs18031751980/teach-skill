# 软件开发讲解的针对性指导

按主技能确定范围，围绕代码或系统实际承担的职责解释。逐行说明仍由代码解释模式负责，本指南补充设计、协作边界与工程取舍，不重复语法。

## 把局部代码放进执行关系

从输入到输出说明关键调用和数据变化，区分接口承诺与内部实现。需要时追踪对象所有权、可变状态、资源生命周期、错误传播和并发访问，避免仅把函数名改写成中文。

例如解释文件写入时，可按问题说明谁打开文件、谁关闭、失败如何返回、调用者会观察到什么。只问一个参数时不自动扩展成完整架构设计。

## 解释取舍而不背模式名

先说明当前需求或约束，再解释分层、抽象、依赖注入、缓存等选择解决哪个具体问题及带来的成本。比较方案应保持相同场景，不用“更优雅”“更解耦”代替因果；简单实现已满足约束时，不为教学硬加设计模式。

讲复用时区分稳定共同点与偶然相似；讲 API 时说明输入约束、返回值和失败契约；讲并发时说明共享状态与交错过程。不要把进程、线程、任务和异步调用当成可互换术语。

## 用变化和失败帮助理解

在适合的问题中，用一个具体需求变化或失败输入演示设计的影响。例如支付请求重试可能造成重复副作用；应先解释操作的语义和去重依据，再讨论幂等处理，不能笼统保证“加重试就更可靠”。

调试讲解沿复现、观察、假设和验证推进，区分症状与原因；测试讲解说明它验证哪个可观察契约及遗漏风险，不按测试数或覆盖率百分比证明正确。性能结论联系测量条件，不将推测当基准测试结果。

提供可运行示例时保留必要依赖与接口，说明如何调用及预期行为；教学简化需要注明与实际系统的相关差异。涉及发布、迁移或外部写入时只解释所问机制，不因教学自动执行。

同次内部复核关注讲解是否与实际代码、接口、状态和失败路径一致，以及取舍是否有当前情境依据。

## 按工程主题选择讲解重点

按用户实际卡点选择下列子主题。每段中的输入和数字均为教学条件；换到用户材料时重新核对，不能把示例答案直接套用。只输出当前问题所需的解释，不照搬本文件的备课结构。

### 语言与对象模型

卡点是“为什么改 backup 影响 original”，以 Python original=[1,2]、backup=original、backup.append(3) 展示两个名称引用同一列表；再用 backup=original.copy() 对比顶层列表分离。若元素是嵌套可变对象，浅拷贝仍可能共享内层对象。

若问参数传递、生命周期或值类型，按当前语言解释，不沿用 Python 示例推出其他语言行为。区分重新绑定变量和修改对象，而不是只说“引用类型”。

### 模块与接口

卡点是“拆接口有什么用”，以业务逻辑依赖读取记录的契约为例：由文件读取换成数据库读取时，返回语义稳定才能让调用者不变。指出应保持哪些字段和错误含义，再讨论替换实现的成本。

若两个模块只在语法上相似但变化原因不同，不强行抽同一基类；若问依赖方向，画真实调用与持有关系，不以文件夹层级证明分层合理。

### API 与错误契约

卡点是“返回空列表还是抛异常”，用查询记录区分三种情况：合法查询无匹配、参数非法、数据源暂不可用。如果都返回 []，调用者无法决定应显示空结果、提示修正还是重试。契约须按实际产品决定，不能机械规定某一种错误形式最好。

若涉及副作用，说明出错前是否可能已经部分完成；若涉及返回格式，核对调用者和兼容性，不仅修改函数内部。

### 并发与同步

卡点是“最终库存没负数，为何超卖”，沿下文库存例子画出读、判断、写的交错。若改用条件更新，说明“库存大于零才扣减”是否在实际存储系统中作为整体执行，并以受影响记录数决定是否成功。

若使用进程内锁，明确它保护哪些参与者，不能覆盖其他进程或绕过该锁的写入。若问死锁，改为追踪资源获取顺序，而不是继续分析这一个丢失更新场景。

### 数据库与事务

卡点是“一个事务中两次查询为何不同”，在明确的 PostgreSQL Read Committed 示例中，让 T1 首次查询、T2 更新并提交、T1 再查询，说明后一个普通查询可以看到新提交值；对比更高隔离语义时引用具体产品说明。

若问事务原子性，改为追踪本事务内成功与失败的写入；若问外部消息或邮件，说明它们是否处于同一原子提交边界，不能认为回滚数据库会撤回外部副作用。

### 缓存与消息

卡点是“同一消息处理了两次”，用消费者完成业务写入后、确认消息前失败的场景说明可能重投。解释业务去重标识、写入与去重记录的原子关系；仅把 message ID 存在内存里不自动覆盖重启情形。

若问缓存旧值，追踪键、写入及失效时序；若问顺序，明确按分区、键还是全局约束。不将某个中间件配置推广成所有缓存或消息系统的保证。

### 测试

卡点是“测试通过为何仍出错”，用边界契约说明：函数承诺接受非负整数，只测试输入 1、2 无法观察 0 是否被错误拒绝。选择能区分预期与错误行为的边界，不只是增加相同路径的样例数量。

若 mock 完全替代了真实失败来源，说明还需要在哪一层验证契约衔接；若问回归测试，先给可复现输入与可观察错误，再验证修正，不只断言调用次数。

### 性能

卡点是“局部快十倍为何整体没快十倍”，设串行流程原总耗时 100 单位，其中优化段占 10；该段降至 1，其他不变，总耗时仍为 91，整体加速约 1.10 倍。明确这是演示条件，不是实测数据。

若问吞吐，联系并发量、排队和资源瓶颈；若问尾延迟，关注分布而非只有均值。异步、缓存或并行是否有益取决于瓶颈，不能只比较代码行数。

### 构建与依赖

卡点是“同一代码为什么换环境失败”，依次核对实际解释器或运行时、解析到的依赖版本、构建目标及启动配置，定位第一个不同点。例：锁文件相同也不自动保证外部系统库、操作系统与架构相同。

若是编译找不到符号，区分源码接口、生成代码和链接依赖；若是运行时缺库，追踪部署产物与加载路径。不要把重装全部依赖当作第一条教学步骤。

### 重构与迁移

卡点是“内部改名为何外部会坏”，用对外返回字段由 name 改为 full_name 的例子指出，客户端若仍读取 name，行为就已经改变。先确定边界内重构还是契约迁移，再讨论兼容策略。

若数据库增加必填字段，追踪旧行怎样得到值、旧程序如何继续写入以及新读路径何时启用。部署顺序与数据回填需根据实际系统安排，不把“代码能启动”当成迁移结束。

## 用具体交错说明并发问题

例如两个执行者都读到库存为 1，各自在本地判断可扣减，随后都写回 0。最终数值看起来合法，却可能允许两次购买；说明问题需追踪“读取—判断—写入”整体，而不只看最后一次赋值。

讲解锁、条件更新或事务方案时，联系保护范围和实际存储系统保证。数据库隔离应按具体产品及级别说明；例如 PostgreSQL 的 Read Committed 与 Repeatable Read 对查询快照的处理不同，不应笼统宣称“事务内所有查询总是读同一版本”。[PostgreSQL 事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)

## 从观察到解释的调试教学

依据报错或异常结果，先确定实际输入、运行路径与最小复现。提出与观察相符的假设，说明用哪条日志、断点或测试区分它与其他解释；拿到证据后再解释修复。没有运行条件时明确哪些是推断，不编造日志。

追问“为什么这样改就好了”时，连接原先失败的条件、修复改变的行为和仍需满足的边界；不要只说“兼容性问题”或“环境问题”。能够局部验证的修正不扩展为无关重构。

## 用需求变化解释设计取舍

若引入接口是为了替换外部实现，展示替换时哪个调用者无需改变，以及新增抽象带来的维护成本。若拆分模块是为了分离变化频率不同的职责，指出两类变化的真实差异。比较方案时以同一需求和约束为基础，不排列脱离情境的优缺点清单。

涉及幂等与重试时，说明失败发生在请求发送前、执行中还是成功但响应丢失之后；这些情形影响能否安全重试。取消请求也不自动代表远端副作用已经撤销。只讨论当前系统实际存在的机制。
