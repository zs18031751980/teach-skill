# Web 开发讲解的针对性指导

按主技能确定范围。解释技术不等于授权搭建、部署网站；实际开发任务遵循用户另行给定的范围。框架和 API 行为涉及版本时查对应官方资料，不把一个框架的机制当作整个 Web 的规则。

## 从一次交互追踪机制

按当前疑点沿实际链路解释：用户操作、事件处理、状态变化、请求、服务端处理、响应以及界面更新。明确代码在哪里执行、哪一端持有状态、数据怎样经过接口；只展开与本次问题相关的环节，不每次从 DNS 讲起。

## 用现象定位层次

教学示例同时说明预期画面或响应，以及能观察该过程的位置，如 Network、Console 或服务端日志。故障讲解先依据症状和证据缩小范围，不连续给用户一串互不相干的配置修改。

例如 `fetch` 收到 HTTP 404 时通常仍得到 Response，而非仅因 404 自动进入 Promise 的拒绝分支；需要检查状态或 `response.ok`，再决定如何显示错误。网络失败与响应正文解析失败是不同阶段的问题。[MDN Fetch 指南](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

跨域问题说明浏览器的响应访问限制与服务端配置关系；不能把 `no-cors` 说成让前端任意读取跨域响应的修复。只解释当前请求需要的规则，不默认引入认证系统设计。

## 保持示例可理解

提供代码时交代必要文件位置、运行前提和可见结果，避免用大量脚手架盖住核心机制。交互教学涉及相关状态时，说明加载、空结果或失败反馈；表单与页面结构按需要讲标签、键盘操作和语义。它们不是每个语法问答的固定附加任务。

同次内部复核关注执行环境、数据/状态流、观察结果和版本前提是否一致，不把“构建成功”当作界面行为已经验证。

## 按前后端问题定位讲解层次

| 主题 | 优先追踪什么 | 示例应让用户看到什么 | 不应混淆什么 |
|------|--------------|----------------------|--------------|
| HTML 与表单 | 元素语义、名称与值、提交行为 | 输入怎样进入请求、标签怎样关联控件 | 外观相似不等于语义或键盘行为相同 |
| CSS 布局 | 包含块、尺寸约束、布局上下文与层叠 | 改变一项约束后尺寸或位置怎样变化 | 不先检查容器和布局，就给子元素堆定位属性 |
| JavaScript 执行 | 当前调用栈、任务与微任务、闭包引用 | 为什么日志或回调按这一顺序发生 | 浏览器与服务端运行时的调度细节不能无条件互换 |
| 组件状态 | 状态归属、更新来源、依赖与视图 | 输入变化怎样传播至界面，旧值为何出现 | 不能把“变量改变”“状态更新”“DOM 更新”视为同一动作 |
| 请求与错误 | 请求发送、收到响应、检查状态、解析正文 | HTTP 错误、网络问题和解析失败的不同表现 | HTTP 成功不等于业务成功；异常处理不能只照顾网络错误 |
| 服务端接口 | 路由、校验、业务处理、持久化与返回 | 请求字段如何被检查和使用，错误怎样反馈 | 前端校验不能代替服务端约束；CORS 不能代替访问权限 |
| 缓存与数据刷新 | 谁缓存、缓存键、何时失效、何时重新读取 | 更新后为什么仍显示旧数据 | 浏览器缓存、服务端缓存与组件内存状态不是同一层 |
| 渲染与路由 | 哪部分在服务器产生、何时到浏览器执行 | 首次加载、交互和路由变化分别发生什么 | CSR、SSR、静态生成的行为取决于实现，不只按名称推断 |
| 可访问性与响应式 | 语义、焦点、键盘路径、内容尺寸 | 不依赖鼠标时的操作、窄屏下的实际布局 | 看上去能点击不等于所有用户都能操作 |
| 构建与部署 | 源码、构建产物、运行时配置及请求目的地 | 本地与部署环境的差异出现在哪一层 | 编译期注入与运行时环境变量不同；前端产物不能承载秘密 |

## 把异步问题变成可观察顺序

浏览器事件循环的教学可以用同步输出、已解决 Promise 的回调和定时器展示顺序，但要交代任务来源和运行环境，再解释为何发生。当前任务中的同步代码先完成；微任务在相应检查点处理；定时器延迟不代表回调能准时执行。[MDN JavaScript 执行模型](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)

不要只让用户背“微任务优先”：把回调何时加入队列、栈何时清空与输出位置对应起来。只有问题涉及具体框架调度时，才继续读该框架资料。

## 请求顺序与界面状态

搜索框连续发出 A、B 两个请求时，A 可能比 B 晚完成。若都直接写入同一结果状态，旧查询可能覆盖新查询。可按任务说明取消请求、请求标识或结果有效性判断解决的是哪个问题，不把“用了 await”当作避免竞争的保证。

对加载、成功、空结果与错误状态，沿实际界面行为说明；不要为了补齐状态表虚构产品需求。接口错误示例应同时交代用户能看到的反馈和开发者用于定位的证据，不能把堆栈原文当作用户提示。

## 代码与观察位置对应

给跨文件示例时，标明哪些代码属于浏览器、服务端或构建配置，以及必要的运行入口。修改一个关键变量或样式就能验证的例子，不创建完整项目。需要真实页面验证时，观察交互与网络行为，不以静态代码阅读代替实测。

用户反馈“没有变化”时，先查相关的状态、样式来源、请求或产物是否实际被使用，再解释修正；不默认推荐重装依赖、关闭安全限制或清空所有配置。
